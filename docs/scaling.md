# 训练规模与训练信号：现状、先前项目、选项（T4b.6 / T4b.7 / T4e.1）

从零开始的 PPO 自博弈在 4 核 CPU 的预算内进展很小（[benchmarks.md](benchmarks.md)「PPO 步长」及其后的 3 小时续训）。本文记录原因、先前项目的做法，
以及两类选项：**扩规模**（[#60](https://github.com/n0tevi1/ygorl/issues/60)）与**提高每份算力的训练信号**
（[#61](https://github.com/n0tevi1/ygorl/issues/61)、[#62](https://github.com/n0tevi1/ygorl/issues/62)）。
与设计文档冲突的选项都标出来了：它们只作为默认关闭的实验开关，采用前先改设计。

## 1. 现状（2026-09-23，4 核云容器、无 GPU）

| 项 | 数字 |
|----|------|
| 端到端 `Trainer.step()`（默认配置、32 局 × 64 步） | 386–415 行/秒 |
| 收集 | 约 1,300 决策/秒，其中 83% 是网络推理（每次约 16 行） |
| 一次更新（2,048 行，4 轮 × 256） | 3.5–3.8 s |
| 引擎上限（C++ 步进、不带网络，T2.7） | 约 2,900 决策/秒/核 |
| 从零训练 3 小时（单牌组对） | 约 4×10⁶ 个决策、3,800 局；对 Greedy 0.05 → 约 0.15 |

瓶颈在网络的推理与更新，不在引擎。

## 2. 为什么多训练几乎不动

从零训练 680 次更新的指标（每段均值）：每次更新策略都有移动（`approx_kl` 约 0.009），但熵（1.22–1.29）、每局决策数（约 1,050–1,220）、
对自己旧快照的胜率（0.44–0.59）都没有趋势：梯度以噪声为主。原因：

1. **长时程、稀疏奖励**：每局约 1,000 个引擎决策、约 450 个训练行，只有终局的胜负；三小时只有约 3,800 局。
   旧日志的 critic 解释方差约 0.97 是对自举训练目标的拟合度，不能据此声称它解释了 97% 的真实终局胜负，
   也不能推导其中多少是策略无法改变的方差。真实终局预测与动作差需要单独验证；见
   [2026-10-04 终局目标对照](spikes/terminal-mc-2026-10-04.md)。
2. **关键行为几乎碰不到**：接近随机的策略很少完整地「进战斗阶段 → 攻击 → 选对象」，更少走完长 combo；
   对局约 45–50 回合、多以卡组耗尽结束。策略梯度只能强化试到过的东西（[bc.md](bc.md)「根因分析」对 BC 得出同样的结论）。
3. **单牌组对的不对称**：驾驶 kashtira 未训练时对 Random 就约 0.93–0.95，驾驶 snake_eye 约 0.05–0.25。
4. **自博弈的对手太弱**：早期的对手是接近随机的自己。
5. **评估分辨率**：80 局约 ±0.1、每套牌 40 局约 ±0.15、训练中的 16 局约 ±0.25。

## 4. 选项

### 4.1 扩规模（#60）

**GPU 还是 CPU**：现在约 80–90% 的时间花在网络上（收集时的推理占收集的 83%，更新每 2,048 行 3.5–3.8 s），这部分可以放到 GPU；
引擎（C++ 核心 + 编码）约 2,900 决策/秒/核，只能在 CPU 上。本仓库的网络很小（136 万参数），一块消费级 GPU 就能把网络的开销压到很低，
之后吞吐由 CPU 核数决定——大约是「1 块 GPU 配几十个核」的比例（ygo-agent 多牌组的配置是 8 块 4090 + 128 核）。致死搜索 / PIMC、求解器示范、
评估对局也都主要吃 CPU。换成默认的大网络（356 万参数）、更长的事件窗口、信念头与文本嵌入会加重 GPU 的份额，但一块中高端消费级 GPU 应该仍然够。
所以：先加一块 GPU（12–24 GB 显存足够）去掉当前的主要开销，之后按核数扩。

### Colab

**2026-10-08 恢复试验**：新的 [L4 恢复协议](spikes/colab-recovery-2026-10-08.md) 将不可变 checkpoint 与对应指标前缀一起回传，
验证 SHA、大小、训练状态、环境、计数和连续更新编号后才原子提升本机 latest。控制器持有运行锁，worker 检查有期限的 lease；
换机前必须确认旧会话已终止。每台 VM 设独立释放定时器，试验限定总时间、分配次数和计算单元预算。
`tools/colab_checkpoint.py` 是可复用的完整性逻辑；`colab_worker.py` / `colab_pilot.py` 是本次固定身份的工程试验，尚不是通用槽位调度器。
入口为 `PYTHONPATH=src .venv/bin/python tools/colab_pilot.py --root out/research/colab-recovery-2026-10-08`，
依赖该产物目录里的预先核验源码包、bootstrap、源检查点清单和已准备的首台会话，不能对新目录直接运行或并行启动。
每次 pilot 的 `identity.json` 绑定源码包与三个 driver 的 SHA；`events.jsonl`、`remote-*.json`、`durable/latest.json` 保留证据。

恢复不等于未中断训练的逐步重放：原生进行中对局没有序列化，会重新开始；首次 ROCm→CUDA 迁移明确重置设备 RNG，
后续 CUDA→CUDA 才逐项验证保存状态完全相同。硬件迁移数据独立记录，不混入已登记的 ROCm 棋力主试验。

本次两台 L4 的主动中断恢复已通过：连续8更新、131,072行、842个正常终局，0错误/截断，完整状态及指标前缀核验一致。
step内443 rows/s，包含重建/上传/控制重试的控制器墙钟约13.9分钟，实际余额减少0.83 CU；结束时无活动会话。
短试验不证明单机加速或棋力改善，后续用途是独立并行容量。准备/同步阶段抢占恢复、跨控制器重启、多运行队列仍未交付，#89保持开放。

以下机器、速度、会话限制和回收时间为 **2026-09-25 历史实测**，不能据此推断当前账号配额或长 rollout 的速度：

用 Google Colab CLI（`google-colab-cli`，`colab new --gpu L4`、`upload`、`exec -f`、`download`）把一部分训练搬到云端。账号的订阅附带 200 计算单元。

**机器**：
- L4 运行时：12 vCPU（Xeon 2.2 GHz）、52 GB 内存、L4 23 GB；约 1.54 单元 / 小时。
- 镜像自带 cmake / g++ 与 Python 3.13。项目用 uv 装 3.11，`uv sync --extra train` 得到 CUDA 版 torch，C++ 扩展直接编译通过。

**吞吐与瓶颈**：
- 训练基准：`tools/bench_train.py`，语料训练集，128 局 × 16 步。
- 单跑：收集 0.55 s + 更新 0.95 s / 次，约 37 次更新 / 分钟。env / collect / torch 线程加倍都在噪声内。**瓶颈是 GPU 上的 PPO 更新**（S5、#72–#77）。
- 正式运行：单跑约 20 次更新 / 分钟，同一台两跑各约 12 次 / 分钟，另含评估和快照对手。
- 对照：本机与其它 GPU 负载共享时，四跑各约 7–8 次 / 分钟。

**限制（实测）**：
- 同时最多 2 个会话，第三个 `colab new` 被拒（412）。
- **VM 会被无预警回收**：三台在创建后 25–55 分钟消失，保活请求突然返回 404，没有任何原因。其中两台在同一时刻被回收，像是账号级限制，而不是个别机器故障。能排除的原因：
  - 不是闲置（保活正常、GPU 满载）；
  - 不是内存（同负载 52 GB 只用 6 GB）；
  - 不是我们自己停的（日志里没有 unassign）。
- 上传接口拒绝约 100 MB 以上的单个文件，要分块上传、在 VM 上拼接。检查点与 `best.pt` 约 120–130 MB，同样要分块。
- CLI 0.7.2 钉的 `jupyter-kernel-client==0.8` 缺 `JupyterSubprotocol`：在工具环境里装 0.9 可修；从 stdin 传代码会挂住，要用 `exec -f 文件`。

**可恢复执行**：本机的调度脚本每个「槽位」管一台 VM、串行跑若干个运行。
- 每 4 分钟把运行目录拷回本机：`checkpoints/latest.pt` 每 10 次更新写一次，拷回前先验证能加载。
- VM 消失时新建一台，上传代码、数据和最新状态，然后用 `train_ppo.py --resume latest.pt --updates <剩余>` 续跑。
- 丢失的进度约等于一个同步间隔。
- 这是实验运维脚本，不在仓库里；把它做成正式功能是 #83 的一部分。

### 4.3 搜索与 RL 结合（#62）

先做对局时的「致死搜索」兜底，量出上限；值得的话把搜索器搬进 C++ 训练路径当老师（专家迭代，蒸馏进策略）；长期是用信念头采样的 PIMC。
阶段 A 已做（`lethal:<agent>`）：包在 K 外面对 Random 0.910 → 0.925、对 Greedy 0.550 → 0.555，在噪声以内——K 自己已经打得出绝大多数斩杀，
所以只为斩杀做阶段 B 不值得（[benchmarks.md](benchmarks.md)「致死搜索原型」）。
阶段 B 改为：只有当搜索器扩展到「本回合之后仍占优」的一般局面（而不只是斩杀）时才值得做，届时与 C（PIMC）合并考虑；
阶段 A 的影子对局 + 快照推演框架可以直接复用。

## 5. 评估方法

- 对比一律用同一批对局（`ygorl arena tests/decks` 的 100 个有序配对 × 1 对种子 = 200 局）上的配对差，并给 Wilson 区间。
- Random 已接近饱和（0.9 上下），主要看对 Greedy 与对固定强检查点（b2s、P4o）的胜率。
- 待做：四重配对（先后攻 × 牌组交换）与多种子；一个臂一个种子的结论都要标「单种子」。
- Greedy 也在接近饱和（最好的检查点 0.6–0.7）。之后以**策略对局矩阵**（检查点、Greedy、Random、`lethal:` 包装之间两两对局，Nash / alpha-rank 排名，可增量加入）作强度尺子（#83）。

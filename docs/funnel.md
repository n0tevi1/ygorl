# 漏斗第一层：求解器起手分析（`ygorl.build.funnel`，T5.6）

> 对应设计文档 [05-deck-building.md](design/05-deck-building.md)「ygo-combo-solver 作漏斗第一层：最佳线存在性 + 抗手坑率（`--fire`）替代单纯的起手概率」
> 与 [06-architecture.md](design/06-architecture.md)「漏斗 (1) 求解器起手分析（最佳线存在性、卡手率、抗手坑率）」「描述符 = {…, combo 长度, 卡手率}」，
> 工程计划 T5.6（[#43](https://github.com/n0tevi1/ygorl/issues/43)）。代码在 `src/ygorl/build/funnel.py` 与 `src/ygorl/build/first_turn.py`，
> 求解器本身见 [solver.md](solver.md)（T4a.1），基因型见 [genotype.md](genotype.md)（T5.5）。

候选牌组（或基因型解码出的牌组）抽固定种子的一批起手，每手交给 T4a.1 求解器找到目标场面的展开线；找到的线再在 `--fire` 手坑下重测。
汇总成：最佳线存在率、卡手率（含 Wilson 区间）、抗手坑率、combo 长度与评估耗时；再给出一个廉价的通过 / 淘汰判定和供 QD 档案（T5.8）使用的描述符。

```
ygorl.build.funnel       FunnelConfig / evaluate_deck / evaluate_genotype → FunnelResult；FunnelFilter；paired_table / mcnemar_exact
ygorl.build.first_turn   「真实首回合」：标准对局里重放求解器的线、Greedy、随机探索 rollout（验证用）
tools/funnel_eval.py     批量评估 .ydk，每套牌一行 JSON（可续跑）
tools/validate_funnel.py 验收实验：漏斗卡手 vs 真实首回合 / 大预算求解器的配对检验与耗时
tools/funnel_budget.py   预算研究：手数 × 每手求解时间 × fire_ms 的误差、排序、过滤一致性与吞吐（--fire 扫描 + 汇总表）
```

## 用法

```python
from ygorl.build.funnel import FunnelConfig, FunnelFilter, evaluate_deck, evaluate_genotype
from ygorl.cards.ydk import load_ydk

cfg = FunnelConfig(hands=12, solve_ms=5000, fire=(14558127,), fire_ms=3000, workers=2)
res = evaluate_deck(load_ydk("tests/decks/labrynth.ydk"), ["1225009", "5380979@szone:fd"], cfg, filter=FunnelFilter(max_brick_rate=0.5))
res.passed, res.reasons            # 过滤结论（淘汰时给出原因）
res.brick_rate, res.brick_interval(), res.hand_trap_survival, res.combo_length()
res.descriptors()                  # {"brick_rate", "combo_length", "hand_trap_survival"}，供 T5.8
res.solver_s, res.within_budget    # 求解器进程秒与预算
res.to_json()                      # 可存档（format "ygorl-funnel"），FunnelResult.from_json 读回

res = evaluate_genotype(space, g, targets, cfg, name="elite-17")   # space.decode(g) 后同上；结果带 genotype_to_json(g)
```

```bash
export YGORL_COMBO_SOLVER=build/combo-solver/bin/combosolver       # 或先 tools/build_combo_solver.sh
uv run python tools/funnel_eval.py tests/decks --hands 12 --workers 2                       # 默认带过滤与早停
uv run python tools/funnel_eval.py tests/decks --no-filter --keep-demos --out out/funnel/validate.jsonl
uv run python tools/validate_funnel.py out/funnel/validate.jsonl --rollouts 1000 --reference-ms 30000 --workers 2
```

`targets` 是一个目标场面（卡片密码列表，语法同 [solver.md](solver.md#目标场面)），或若干个备选场面（列表的列表）：
一手按顺序尝试备选，到达任一即算有线（有备选时卡手的代价是 备选数 × `solve_ms`）。

## 定义

| 量 | 定义 |
|----|------|
| 起手 | 第 `i` 手 = 主机洗牌 `hand_seed(seed, "funnel", i)` 的顶上 5 张（`sample_hand`，与对局、求解器相同）。种子**不含牌组名**：同样张数的牌组用同一组洗牌置换（共同随机数），候选之间的比较是配对的；`opening_hands(deck, cfg)` 列出这些起手 |
| 有线 / 卡手（brick） | 求解器在 `solve_ms` 内找到**且在我们核心里重放验证通过**的线（`solve_hand` 的 `solved`）→ 有线；预算内没找到（`unsolved`）→ 卡手。`error` / `unverified` 是工具链故障，不计入分母，单独计数 |
| 最佳线存在率 / 卡手率 | 有线手数 / 非错误手数；卡手率 = 1 − 存在率，附 95% Wilson 区间 |
| 手坑存活 | 对有线的手，按 `--fire` 手坑逐张跑 `solve_fire`：`no_window`（这条线上手坑无可发动时点）算存活；`solved` 且求解器**从每个**可发动时点都恢复了终场（`converted == windows`，对手自选时点）算存活；其余不存活 |
| 抗手坑率 `hand_trap_survival` | 「起手有线**且**对每张 `--fire` 手坑都存活」的手数 / 非错误手数（无条件）；`survival(fire, given_line=True)` 是以有线为条件的比例；`window_recovery(fire)` 是全部可发动时点中被恢复的比例（较宽松的补充指标） |
| combo 长度 | 有线手的最佳线（求解器评分最优）：`combo_actions` = 召唤与发动次数（求解器评分 `actions`），`combo_decisions` = 来自求解器的动作步数；报告均值、中位数、最小、最大 |
| 耗时 | `solver_s` = 各手求解器墙钟之和（plain + fire），即**单线程求解器进程秒**，与并行进程数无关；`wall_s` 是整套评估的墙钟 |

`FunnelResult.descriptors()`：`brick_rate`、`combo_length`（`combo_actions` 均值）、`hand_trap_survival`。
没有一手有线时 `combo_length` 为 NaN，不带 `--fire` 时 `hand_trap_survival` 为 NaN；这类牌组先被过滤器淘汰，不进档案。
设计文档描述符里的「手坑数」直接取基因型的 `role_counts(g)["hand_trap"]`（T5.5），不在这里算。

## 过滤器与早停（`FunnelFilter`）

- `max_brick_rate`（默认 0.5）：卡手率上限；`min_hand_trap_survival`（默认 0，即不设门槛）：抗手坑率下限；全部手都是 `error` 的牌组淘汰。
- **早停**：已出现的卡手数超过 `max_brick_rate × 计划手数` 时，这套牌已不可能通过，剩余的手不再求解（`stopped_early`，结论为淘汰）。
  卡手每手要花满 `solve_ms`，而随机基因型大多是高卡手率，早停把它们的成本压到约 `max_brick_rate × hands × solve_ms`。
- 过滤器只看漏斗第一层自己的量；是否把 `brick_rate` 的 Wilson 上界、抗手坑率等作为 fitness 的一部分由 T5.8 决定。

## 预算

设计文档与工程计划没有给出第一层的数字预算，这里按用途定为 **每套牌 120 求解器进程秒**（`DEFAULT_BUDGET_S`）：
第一层要在代理模型（T5.7）和真实对局（第三层：每候选微调 B 局 + 数百局评估，按进程小时计）之前把大部分候选筛掉，
目标是 16 核机器一天能筛约 1 万个候选（16 × 86,400 / 10,000 ≈ 138 秒 / 套）。默认参数（12 手、`solve_ms` 5 秒、Ash Blossom 一张、`fire_ms` 3 秒）
的最坏情况是 12 × 5 秒卡手 = 60 秒 plain，再加有线手的 `--fire`。**这个数字是工程取值，需要设计方确认**（见文末「待定」）。
实测评估见下文「预算研究」：120 秒 / 套合理；但每手 5 秒会系统性高估长 combo 牌组的卡手率，建议改为每手 10 秒（仍在 120 秒均值内）。

## 验收实验：卡手率与真实首回合一致（配对检验）

### 设计

同一批起手上比较两种判定（配对）：

- **漏斗**：上面的默认配置，每手 `solved` / `unsolved`。
- **真实首回合**（`ygorl.build.first_turn`）：用我们的主机开一局**标准对局**——同样的卡组顺序（起手在顶上）、同样的核心种子字、同样的白板对手，
  但**不带 `DUEL_PSEUDO_SHUFFLE`**（效果里的「洗切卡组」真的洗）；先攻玩家打完第 1 回合，到第 2 回合第一个决策时检查目标卡是否在场。三个玩家：
  1. **求解器的线**（有线的手）：在伪洗牌对局里逐步重放示范线，每一步在真实对局的候选里按「做什么」（动作种类、卡片密码、区域；卡组 / 手牌内的序号不比较）匹配；
     匹配不到即线在真实对局里断了，之后被动结束回合再检查场面；
  2. **Greedy**（`GreedyAgent`，4 个种子）；
  3. **随机探索**（`ExplorerAgent`：空闲阶段以 0.9 概率做一个非阶段切换的动作，其余决策均匀随机），从开局快照出发 1,000 次 rollout。

  任一玩家到达目标即该手「真实有线」。
- **参照求解器**：漏斗判为卡手的手用 6 倍预算（30 秒、另一个求解器种子）再解一次。

比较四组配对：漏斗 vs (a) 真实首回合（三个玩家合并），(b) 只用 Greedy + 随机探索（与求解器独立的玩家），(c) 参照求解器，(d) 已知最佳（a 或 c）。
检验用精确 McNemar（不一致对的二项检验，`mcnemar_exact`），H0：两种判定的卡手率相同。

### 结果：配对检验

| 漏斗卡手 vs … | 两者都卡手 | 只有漏斗卡手 | 只有对方卡手 | 两者都有线 | 漏斗卡手率 | 对方卡手率 | 一致率 | McNemar p |
|------|------|------|------|------|------|------|------|------|
| (a) 真实首回合（线 + Greedy + 探索） | 48 | 3 | 1 | 68 | 0.425 | 0.408 | 96.7% | **0.625** |
| (b) 仅 Greedy + 探索 | 48 | 3 | 11 | 58 | 0.425 | 0.492 | 88.3% | 0.057 |
| (c) 参照求解器（30 秒） | 47 | 4 | 0 | 69 | 0.425 | 0.392 | 96.7% | 0.125 |
| (d) 已知最佳（a 或 c） | 46 | 5 | 0 | 69 | 0.425 | 0.383 | 95.8% | 0.063 |

- **(a) 验收项**：漏斗卡手率 42.5% 与真实首回合 40.8% 在 120 对上无显著差异（p = 0.63），一致率 96.7%。
  - 「只有对方卡手」1 手（purrely 第 4 手）：求解器的线在真实对局第 22 步断开——Purrely 的效果先洗切卡组再看卡组顶，伪洗牌下与真实洗牌下顶上的卡不同（[solver.md 的限制](solver.md#限制)）。
    69 条线中 68 条在真实对局里原样走通并到达目标。
  - 「只有漏斗卡手」3 手：snake_eye 第 1、7 手与 purrely 第 10 手，随机探索在 1,000 次 rollout 中各有 1 次到达目标；其中两手参照求解器 30 秒也解出（snake_eye 第 1 手 30 秒仍未解出）。
- **(b)**：去掉求解器的线后，Greedy 与随机探索在漏斗有线的 69 手里只到达 58 手（Greedy 20 手；480 局 Greedy 首回合只有 46 局到达目标），
  独立玩家的卡手率 49.2% 高于漏斗——弱玩家的「卡手」混着「不会打」，不能单独作为真值；这一行 p = 0.057，接近显著。
- **(c)**：6 倍预算只多解出 4 / 51 个卡手（purrely 2、snake_eye 1、tenpai 1，用时 5.5–17.1 秒），方向一致（漏斗只会高估卡手）。
- **(d) 偏差**：相对已知最佳，漏斗把 5 / 120 = 4.2% 的手误判为卡手（95% Clopper-Pearson 区间 1.4%–9.5%），没有反向误判；
  p = 0.063 未过 0.05，但全部不一致都在同一方向，检验的功效有限（5 个不一致对时 p 的最小可能值就是 0.0625）。
  所以准确的表述是：**在 120 手的样本上未检出差异；漏斗卡手率存在约 4 个百分点的系统性高估（预算不足导致的假卡手），样本增大后很可能显著**。
  对过滤器而言这是保守方向（误淘汰而非误放行），对描述符而言是近似同幅度的平移。

## 预算研究：每套 120 秒是否合理

### 问题与判据

第一层是廉价过滤器和 QD 描述符的来源，所以预算是否够用不看绝对精度，而看**相对一个大得多的预算**：
(a) 过滤结论是否稳定；(b) 牌组间的排序与描述符分箱是否稳定；(c) 吞吐是否跟得上流水线。
预算有两个旋钮：每套手数 `hands` 决定**抽样噪声**（二项分布，可解析计算），每手求解时间 `solve_ms` 决定**假卡手**（预算内没找到线，只会单向高估卡手）；另有 `fire_ms`。
工具是 `tools/funnel_budget.py`：`fire` 子命令在已有的线上以另一个 `fire_ms` 重跑 `--fire`，`analyze` 子命令读入各次 `funnel_eval.py` 输出，打印本节全部表格并写 JSON。

### 设计

| 运行 | 命令（`tools/funnel_eval.py tests/decks --no-filter --workers 2 …`） | 手 | 用途 |
|------|------|------|------|
| 参照 | `--hands 48 --solve-ms 20000 --fire-ms 3000 --keep-demos` | 10 × 48 = 480（479 有效） | 大预算基准：卡手率、抗手坑率、combo 长度 |
| 直接测 | `--hands 48 --solve-ms 2000 --no-fire`；`--hands 48 --solve-ms 5000 --no-fire`；`--hands 24 --solve-ms 10000 --no-fire` | 480 / 480 / 240 | 每个 `solve_ms` 的卡手判定与每手耗时 |
| 重复 | 验收实验的 5 秒运行（`out/funnel/validate.jsonl`，前 12 手，另一时刻、另一负载） | 120 | 同预算两次运行的差异 |
| `--fire` 扫描 | `tools/funnel_budget.py fire out/funnel/validate.jsonl --fire-ms {1000,3000,10000}` | 69 条线 | 验收实验有线的 69 手，同一条最佳线在不同 `fire_ms` 下的存活判定 |
| 参照的可信度 | 验收实验的真实首回合（`observers.jsonl`）与 30 秒重解（`reference.jsonl`） | 120 | 参照自身还剩多少假卡手 |

```bash
uv run python tools/funnel_budget.py analyze out/budget/ref48_20s.jsonl \
    --direct out/budget/plain48_2s.jsonl --direct out/budget/plain48_5s.jsonl --direct out/budget/plain24_10s.jsonl \
    --direct out/funnel/validate.jsonl --fire-run out/budget/fire_1000.jsonl --fire-run out/budget/fire_3000.jsonl \
    --fire-run out/budget/fire_10000.jsonl --observers out/funnel/observers.jsonl --re-solved out/funnel/reference.jsonl
```

- **每个预算必须直接跑，不能从一次长跑截断推出。** 求解器把 `--solve-ms` 按固定比例分给各阶段（源码里有 `solve_ms / 6`、剩余 × 0.7、剩余 × 0.8 等切分），
  所以同一手在 5 秒预算下 1.2–1.5 秒解出，在 20 秒预算下要 3.8–4.0 秒（前一阶段变长了）；69 手里只有 4 手两者耗时相差 < 0.3 秒。
- 数据：10 套测试牌组、同一组固定种子（第 `i` 手在所有运行里是同一起手），求解器 2 进程 × 1 线程、种子 1；labrynth 第 34 手在参照里是 `unverified`（工具链问题），各表按 479 手计。
- 日期 2026-09-23；机器是 4 核云容器：参照运行期间另有一个 2 线程训练任务（1 分钟负载 2.7–5.8，中位 4.0），其后各运行负载 2.0–4.5。总计约 1 小时 45 分墙钟。

### 结果二：手数 → 抽样噪声，以及合起来的误差

卡手率的抽样标准差是 √(p(1−p)/n)：p = 0.4 时 6 / 12 / 24 / 48 手分别是 0.20 / 0.14 / 0.10 / 0.07（95% 区间半宽 0.39 / 0.28 / 0.20 / 0.14）。
下表把两者合起来（每套牌的偏差取同手配对值，噪声取参照卡手率的二项 SD，RMSE² = 偏差² + SD²，对 10 套取平均），并给出排序、过滤与分箱的稳定性和成本：

| `solve_ms` | 手 | 平均偏差 | 抽样 SD | RMSE | Spearman（前 n 手） | Spearman（自助中位） | 过滤一致（自助） | 同箱率 3 箱 / 5 箱 | 每套求解器秒 均值 / 最大 | 16 核每天套数 |
|------|------|------|------|------|------|------|------|------|------|------|
| 2 秒 | 12 | 11.3 pp | 13.4 pp | 21.5 pp | 0.48 | 0.35 | 0.66 | 0.42 / 0.35 | 45 / 69 | 30,700 |
| 5 秒 | 6 | 6.5 | 19.0 | 21.2 | 0.94 | 0.47 | 0.71 | 0.42 / 0.32 | 34 / 52 | 40,300 |
| **5 秒（默认）** | **12** | **6.5** | **13.4** | **16.4** | **0.70** | **0.59** | **0.74** | **0.52 / 0.42** | **69 / 104** | **20,100** |
| 5 秒 | 24 | 6.5 | 9.5 | 13.3 | 0.73 | 0.69 | 0.78 | 0.58 / 0.47 | 137 / 207 | 10,100 |
| 5 秒 | 48 | 6.5 | 6.7 | 11.5 | 0.82 | 0.74 | 0.82 | 0.63 / 0.51 | 275 / 415 | 5,000 |
| **10 秒** | **12** | **2.9** | **13.4** | **14.4** | **0.73** | 0.57 | 0.73 | 0.47 / 0.38 | **101 / 137** | **13,600** |
| 10 秒 | 24 | 2.9 | 9.5 | 10.8 | 0.78 | 0.65 | 0.77 | 0.53 / 0.42 | 203 / 273 | 6,800 |
| 20 秒 | 6 | 0 | 19.0 | 19.0 | 0.93 | 0.60 | 0.75 | 0.54 / 0.40 | 80 / 105 | 17,300 |
| 20 秒 | 12 | 0 | 13.4 | 13.5 | 0.86 | 0.74 | 0.79 | 0.67 / 0.53 | 160 / 211 | 8,600 |
| 20 秒 | 24 | 0 | 9.5 | 9.5 | 0.89 | 0.84 | 0.83 | 0.77 / 0.65 | 320 / 421 | 4,300 |

- 成本 = 手数 ×（该预算下每手的 plain 求解器秒 + 有线率 × 该牌组参照的 `--fire` 3 秒耗时），不含早停；「前 n 手」是漏斗实际用的前 n 个种子，「自助」是从该预算的全部手里有放回抽 n 手 2,000 次、与参照（48 手 × 20 秒）比较。
  自助值对 20 秒偏乐观（抽的就是参照自己的手），对 10 秒偏悲观（只有 24 手可抽，这 24 手本身与 48 手有抽样差），跨预算比较以 RMSE 为准。
- **12 手时噪声是平均误差的主项**（5 秒：SD 13.4 pp vs 平均偏差 6.5 pp），但偏差集中在少数牌组（5 秒的 RMS 偏差 9.3 pp，10 秒 5.1 pp）。
  等成本比较：5 秒 × 18 手（约 103 秒）与 10 秒 × 12 手（101 秒）的 RMSE 都是约 14.4 pp——总误差一样，区别是前者的误差里有与 combo 长度相关、不会平均掉的一块。
- **排序**：这 10 套测试牌组的参照卡手率彼此很接近（牌组间 SD 0.133，4 套在 0.5 门槛 ±0.08 以内），即使没有偏差，n 手估计与真值的期望相关也只有
  √(牌组间方差 / (牌组间方差 + 噪声方差)) = 0.57 / 0.70 / 0.81 / 0.89（6 / 12 / 24 / 48 手）。按卡手率给相近的牌组排序受手数限制，任何可行的预算都做不到精细；
  候选群体差异大时（随机基因型多在 0.7 以上，好牌组在 0.2–0.4）排序容易得多。
- **过滤**：12 手时 10 套里有 2 套结论与参照不同（都是门槛附近的牌组）。门槛 0.5 下的误判率（二项分布）：

| 真实卡手率 p | 6 手 | 12 手 | 24 手 | 48 手 |
|------|------|------|------|------|
| 0.2 | 0.017 | 0.004 | 0.000 | 0.000 |
| 0.3 | 0.070 | 0.039 | 0.012 | 0.001 |
| 0.4 | 0.179 | 0.158 | 0.114 | 0.060 |
| 0.45 | 0.255 | 0.261 | 0.242 | 0.200 |
| 0.55 | 0.558 | 0.473 | 0.385 | 0.290 |
| 0.6 | 0.456 | 0.335 | 0.213 | 0.103 |
| 0.7 | 0.256 | 0.118 | 0.031 | 0.003 |
| 0.8 | 0.099 | 0.019 | 0.001 | 0.000 |

  12 手对「明显好」（p ≤ 0.3，误淘汰 ≤ 4%）和「明显差」（p ≥ 0.8，误放行 ≤ 2%）的牌组足够；门槛 ±0.1 以内的牌组任何手数都分不清，这是门槛本身的性质。
  假卡手让长 combo 牌组的 p 向上平移，误淘汰的方向正是这些牌组（purrely）。
- **QD 分箱**：卡手率这一维在 12 手下只有约一半概率落在参照的同一箱（3 箱时 0.47–0.67，5 箱时 0.38–0.53），48 手 × 20 秒自己抽样也只有 0.84 / 0.75；
  T5.8 若按卡手率分箱，12 手只撑得起约 3 箱（箱宽 ≈ 0.33 ≈ 12 手的 95% 区间半宽）。

前 n 手（参照运行）与全部 48 手相比：

combo 长度在 12 手时已经很稳定（平均差不到半个动作）；抗手坑率的绝对值小（0.04–0.44），平均差 0.06。

同样 69 条线在不同 `fire_ms` 下（参照 = 10 秒）：

| `fire_ms` | 存活率 | 与 10 秒不一致 | 每条线求解器秒 |
|------|------|------|------|
| 1 秒 | 0.348 | 2（都是 10 秒存活、1 秒不存活） | 1.69 |

`--fire` 不便宜：默认配置下每套约 30 秒花在 `--fire` 上（12 手 × 有线率 × 每手 1.7–8.4 秒，purrely 与 snake_eye 每手约 8 秒），占 5 秒 × 12 手总成本的 43%。

### 结果四：吞吐

| `solve_ms` | 手 | 早停后每套求解器秒：p = 0.4 | p = 0.7 | p = 0.9 |
|------|------|------|------|------|
| 2 秒 | 12 | 49 | 31 | 20 |
| 5 秒 | 12 | 68 | 54 | 41 |
| 10 秒 | 12 | 98 | 90 | 77 |
| 20 秒 | 12 | 159 | 163 | 146 |
| 5 秒 | 24 | 137 | 101 | 77 |
| 10 秒 | 24 | 197 | 170 | 142 |

（按顺序逐手模拟早停：卡手花满该预算的实测卡手耗时，有线手花实测有线耗时 + 平均 `--fire` 耗时；2 进程并行时已在跑的手会多花一点。）

- 120 秒 / 套 ⇒ 16 核每天 11,520 套。随机基因型多是高卡手率，早停后 5 秒预算每套 41–54 秒（每天 2.5–3.4 万套），10 秒预算 77–90 秒（1.5–1.8 万套）。
- 设计文档与工程计划没有给出 T5.8 的档案大小或评估次数。按设计的漏斗顺序（第一层 → 代理模型 → 第三层「微调 B 局 + 数百局评估」），第三层每候选至少约 1 进程小时，
  16 核每天约 384 个；第一层 120 秒约为它的 3%。只要第一层筛的候选不超过第三层的 ~30 倍，第一层就不是瓶颈。
  若 T5.8 把第一层放进 MAP-Elites 的内循环（每代上万个候选都要跑），瓶颈就在这里，那时应由代理模型（T5.7）先筛，第一层只评估代理挑出的候选。

### 结论与建议

1. **总预算 120 秒 / 套合理，保留。** 它对应每天约 1 万套，是第三层每候选成本的百分之几；默认配置每套均值 69 秒、最大 104 秒（本节成本模型；验收实验实测均值 71、最大 116 秒），早停后的淘汰牌组 41–54 秒。
2. **每手 5 秒偏短，这是 120 秒内最该调的一项。** 5 秒的假卡手不是均匀噪声，而是与 combo 长度强相关的系统偏差（snake_eye、purrely +17–19 pp，过滤结论可翻转），多抽手平均不掉。
   **建议 `solve_ms` 改为 10 秒、手数保持 12、`fire_ms` 保持 3 秒**：偏差降到 +2.9 pp（长 combo 牌组 ≤ 3 / 24），RMSE 16.4 → 14.4 pp，
   成本均值 69 → 101 秒（最大 104 → 137 秒），均值仍在 120 秒内，每天约 1.4 万套（早停后淘汰牌组 77–90 秒）。
   严格要求单套 ≤ 120 秒时，可同时把 `fire_ms` 降到 1 秒（每套省约 18 秒，均值约 83 秒；抗手坑判定 2 / 69 偏严；2 秒未测）或把手数降到 10。
   20 秒在 12 手时成本 160 秒、超出预算，偏差再降 2.9 pp 不值这个价。2 秒不可取（+11 pp，snake_eye +38 pp）。
3. **手数保持 12。** 12 手的抽样 SD（约 13 pp）是剩余误差的主项，但加手数的成本是线性的；对过滤器（门槛 0.5）12 手足以区分 p ≤ 0.3 与 p ≥ 0.8，
   对 QD 只撑得起卡手率约 3 箱。更细的分辨率交给 T5.8 的**逐级加预算**（设计文档 5.1：Optuna successive-halving）：所有候选先 12 手，
   进入档案、落在门槛或箱界附近的候选再补到 24–48 手。第 `i` 手的种子与计划手数无关，补测只需再跑第 12–47 个种子（`evaluate_deck` 目前总从第 0 手开始，需要加一个起始序号参数）。
4. **默认值暂未修改**：120 秒保留无需改动；`solve_ms` 5 → 10 秒是一个吞吐与偏差的取舍（等成本的 5 秒 × 18 手总 RMSE 相同，只是误差构成不同），留给设计方确认后再改 `FunnelConfig.solve_ms`（一行，`DEFAULT_BUDGET_S` 不变）。
5. **可复现**：`FunnelConfig.max_rollouts` / `funnel_eval.py --max-rollouts` 已接到求解器的 `--max-rollouts`（每个搜索阶段、每个进程的 rollout 数上限）；
   墙钟 `solve_ms` 仍限制每个阶段，所以要把 `solve_ms` 设得足够大让计数先到。实测 snake_eye 4 手 `--max-rollouts 2000 --solve-ms 60000` 两次运行的线逐手相同（每套约 64 秒）。
   计数预算与秒数的换算因牌组而异，本研究仍用墙钟预算（且 5 秒两次运行在不同负载下 0 / 120 不一致，墙钟预算在当前负载范围内已足够稳定）。

### 本研究的局限

- 只有 10 套测试牌组：`environments/md-2026-09/meta/` 的 20 套真实 meta 牌组与基因型解码的牌组都还没有求解器目标（目标要人给，见下文「局限」），没有纳入；
  测试牌组的卡手率彼此接近，排序类指标因此偏低，不能外推到差异大的候选群体。
- 10 秒只测了前 24 手；10 秒与 20 秒之间、20 秒以上的偏差只能由「参照残余 ≤ 1 / 120」间接约束。
- 墙钟预算：负载更高的机器上同一 `solve_ms` 解出的手会更少；本研究的负载 2–6（4 核）。

## 局限

- **目标场面要人给。** 求解器只判定「到达给定目标」。测试牌组的目标来自 `tests/decks/solver_targets.json`；基因型解码出的牌组还没有自动目标——
  需要从引擎包推出（例如包内额外卡组怪兽作为备选场面），这属于 T5.8 接入时的决定。`evaluate_genotype` 目前要求调用方传目标。
- **卡手 = 预算内没找到。** 求解按墙钟计预算，受机器负载影响，结果不可逐位复现（`--threads 1` + 固定求解器种子只固定 rollout 顺序）；
  实测相对 6 倍预算有约 4 个百分点的假卡手（上节）。需要可复现时可用 `FunnelConfig.max_rollouts`（`--max-rollouts`，见「预算研究」结论 5）。
  预算研究在 48 手上测得 5 秒相对 20 秒的假卡手为 +6.5 pp，集中在长 combo 牌组。
- **伪洗牌。** 求解器的线在 `DUEL_PSEUDO_SHUFFLE` 下成立；依赖「洗牌后看卡组顶」的牌组（本实验中的 purrely）在真实对局里可能断线，漏斗会高估这类牌组的有线率（本实验 1 / 69）。
- **对手是白板、手坑逐张单次。** 抗手坑率只测 `--fire` 列出的手坑、最佳一条线、每个时点发动一次；多张手坑、对手的其它互动不在范围内。
  「存活」要求从每个时点都恢复，比「对手随机时点」严格。
- **验证的「真实首回合」是下界。** Greedy 与随机探索都弱；因此验收检验以「真实首回合玩家 ∪ 求解器的线」为观测，另报了独立玩家与大预算求解器两组对照。
- **样本小。** 每套 12 手时单套卡手率的 Wilson 区间宽约 ±0.25；QD 描述符的分辨率受此限制，T5.8 可按档案格宽调整 `hands`。

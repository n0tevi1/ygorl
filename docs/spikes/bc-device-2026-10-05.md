# BC 显式设备路径（2026-10-05）

现有 `train_bc.py` 不提供设备选择，训练和步指标固定创建 CPU tensors，无法直接用于计划中的 GPU 大网络容量实验。

先约定：默认 CPU 保持兼容，新增显式 `--device cpu|cuda[:index]`（ROCm 也使用 cuda）。
原生 `train_bc` 和 `step_accuracy` 随网络实际设备传递观测与标签；不隐式迁移调用者网络。
CLI 新建/微调/仅评估都应用指定设备，报告和新 checkpoint 记录实际设备及 Torch/ROCm 身份。
检查点仍存 CPU tensors，逐步自由对局在训练/步指标完成后显式迁回 CPU，以保持 NetPolicy 路径兼容。
不引入混合精度或改变优化器、种子、数据与标签范围；不可把设备路径跑通称为容量/强度验收。

验证：真实 ROCm 前向、反向、参数更新和步指标；保存后 CPU 加载指标一致（浮点容差），
CLI CPU/GPU × 两种标签范围均实际微调，并完成 heldout 自由展开，核对设备与数据范围元数据。
随后才用独立冻结数据开展容量实验，吞吐测量需要单列并发环境。

实际验证发现 `BCData.batch(device=...)` 原先只迁移观测，标签仍创建在 CPU；
真实 GPU 测试首先因这个错误失败，修复后 CPU/GPU × 新旧标签范围与保存回读全部通过。
定向测试 **25 passed，8.11 s**。已测实现 **652c0a4** 全套 presubmit
**1,434 passed / 3 skipped，343.36 s**，使用实际 Radeon 8060S / ROCm。
三项跳过是 snapshot 编译选项与两个 opt-in 联网测试；无 hosted checks。
测试期间另有 CPU 搜索诊断，不把测试耗时当 GPU 训练吞吐。
证据保存于 `out/research/bc-device-2026-10-05/`，测试与设备身份工件另行封存。

使用 `tools/train_bc.py --device cuda` 启用 GPU 训练及步指标；默认仍为 CPU。
报告中的 `device` 是实际训练/步指标设备，`opening_device=cpu` 明确自由展开的设备。
新检查点记录 `training_device`，权重仍可在 CPU 加载；这只验证执行路径，不是新策略强度结果。

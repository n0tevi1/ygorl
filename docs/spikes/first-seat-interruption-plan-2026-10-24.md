# 先手「制造断点」与「打断」：研究、规划与设计（2026-10-24）

范围：只做研究与设计，不实现训练功能，也不跑 GPU 训练。目标是让先手学会两件事：回合 1 摆出能打断对手的场面（制造断点），以及在对手回合 2 挑对时点打断。
背景数字见 [rl-methodology-review-2026-10-20.md](rl-methodology-review-2026-10-20.md) §6.2–§6.4、§7.3b–§7.5 与 #439–#443。
基准脚本是 `tools/bench_prefix_fork.py`（本次新增，只用 CPU）。

## 0. 结论先行

1. **能直接复用的开源对局复制：没有。** ygoenv（sbl1996/ygo-agent）和 envpool 都不能复制或快照对局状态。唯一能用的机制是 ygo-combo-solver 的 arena，**我们已经移植并验收过（T2.8，#20 已关闭）**。还缺的是把它接进 C++ 步进环境 `HostDuel` / `HostPool`，工作量是几百行 C++，不需要换框架。
2. **分叉很便宜，从种子重放也不贵。** 实测 77 条求解线、18 套牌，重放到回合 1 结束（回合 2 第一个决策）的中位数是 20 ms，其中 16 ms 是建局本身，跟普通 reset 一样要付。快照恢复中位数 0.40 ms，其中核心部分 0.13 ms。快照只能恢复回拍下它的那一局，所以 A/D 的多个分支要在**同一个槽位里依次跑**，跨槽位起局就用重放。
3. **诊断要补一条（§10 修订）。** 回合 2 的对手线一旦被打断，就交给快照策略接手，而这个策略几乎展不开连招（G 只有 6% 能到达求解器目标）。阶段 0 的配对分支（§10.2，P0b (i)）证实了后果：快照对手下，标签为「不打」的时点有 68% 被反事实判成「打」，换成恢复线后降到 40%。所以**任何一次打断都会把被接手的对手变弱**，训练信号因此偏向「有机会就打」，这和每个 ckpt 都在窗口 1 打灰流丽的表现一致。注意局间比较（§10.1，P0a）看不出断线局学习者更容易赢，先手甚至相反，所以恢复线是 A 的前提，理由是「否则窗口反事实系统性偏向打」，不是「断线局胜率高」。A（窗口反事实）**必须配上合格的恢复对手**。
4. **推荐的第一步**：先做 §6 的阶段 0，纯 CPU，约 1–2 天，同时开工 T1（C++ `HostDuel` 快照）。阶段 0 的 P0b 用现有 Python `DuelSession` 快照和已有的灰流丽恢复线（`--fire` 变体），离线检查窗口反事实与求解器标签的一致性。目标是一致率 ≥ 0.75、平局 ≤ 15%；达到才接进训练循环（A + T6 恢复线），达不到就先修恢复对手。

为什么不能走「序列化」：暂停在 `MSG_SELECT_*` 时，Lua 协程停在效果处理的中间，栈和 upvalue 都在里面。按字段序列化要穷尽核心与脚本的全部状态，做不到（这一点和求解器作者的判断一致）。
内存镜像是唯一可行的办法，它的代价是**快照绑定在拍下它的那个 arena 槽位上**：指针是绝对地址，换个槽位恢复就要重定位，所以不支持。

**结论：不引入外部 env 框架。** 在我们自己的 `HostDuel` / `HostPool` 上补齐快照与前缀起局（§5.2、任务 T1/T2）即可，这也符合 CLAUDE.md「不要引入其它运行时或框架」的约束。

## 3. 实测：前缀起局与分叉的代价（B 的数字）

命令：`uv run --no-sync python tools/bench_prefix_fork.py out/claude-scale/handtrap/lines_train.jsonl --lines 80 --envs 64 --threads 16`。
2026-10-24，本机 AI Max+ 395（32 线程），**测量期间负载 19–32**（其它会话在训练），绝对值偏保守。
样本是 77 条求解线、18 套牌（另有 3 条因撤销规则遮住示范动作而跳过）；先手按线走，后手被动；「回合 1 结束」= 回合 2 的第一个决策。

| 项 | 中位数 | p90 | 最大 |
|---|---:|---:|---:|
| 回合 1 的步数（agent 步） | 52 | 92 | 131 |
| Python `DuelSession` 建局 + 重放到回合 1 结束 | **20.4 ms** | 28.2 | 32.9 |
| 　其中建局并跑到第一个决策（加载脚本、加卡） | 16.4 ms | 22.2 | 24.9 |
| 　同上但开 arena（`snapshots=True`） | 19.7 ms | 27.0 | 33.6 |
| `DuelSession.snapshot()`（核心镜像 + 追踪器深拷贝） | 0.51 ms | 0.72 | 1.28 |
| `DuelSession.restore()` | **0.40 ms** | 0.57 | 0.77 |
| 只算核心：`Duel.snapshot()` / `restore()` | 0.17 / **0.13 ms** | 0.88 / 0.17 | 1.35 / 0.25 |
| arena 已用（≈ 快照大小） | 3.2 MiB | 3.5 | 4.5 |
| C++ `EncodedVecEnv`（1 槽 1 线程）reset + 按线走到回合 1 结束 | 29.6 ms | 40.3 | 74.2 |
| C++ 从回合 2 开始随机打到回合 3（不含网络；30 步） | 5.7 ms | 11.3 | 29.0 |
| C++ 前缀起局吞吐（64 槽、16 线程；逐步走线） | **194 个/秒**（10,000 决策/秒） | | |
| T2 的 `reset(..., prefix)`：前缀起局 / 其中每个前缀动作（另一次测量，负载约 29，建局 31.8 ms） | **43.4 ms / 0.22 ms**；吞吐 257 个/秒 | 54.3 / 0.34 | |

读法：
- **重放的成本几乎全在建局。** 线本身 52 步只占 4 ms（Python）或约 8 ms（C++，每步约 0.16 ms，含编码与 Python 往返）。任何新局都要付 16 ms 建局，所以「从回合 1 结束起局」比普通 reset 只多 25–50%。在训练里，每 1,024 局最多多花约 5 CPU 秒，分到 16 个工作线程上可以忽略。
- **同槽位恢复比重放快约 50×**（0.40 ms 对 20 ms）。C++ 里不用拷 Python 追踪器，估计能降到 0.2 ms 左右。
- **限制**：快照只能恢复到同一局，所以「一个局面分 K 份并行」做不到。可行的做法有两种：同槽位依次分支（A：K=2，每个分支打完对手回合约 6 ms 引擎时间加网络前向），或在 K 个槽位里各自重放（D 的候选评估，每份 20–30 ms）。
- 内存：开 arena 后每局常驻约 3.2 MiB，每多一个快照再加 3.2 MiB。1,024 槽各留 1 个快照约 6.5 GiB 主机内存（假设：Colab L4 高内存规格够用；本机足够）。

## 4. 文献与方法的适用性（研究问题 2）

| 方法 | 要点 | 在「对手回合 2 的单个打断窗口」上 | 在「先手回合 1 展开」上 |
|---|---|---|---|
| Vine 采样（Schulman 等 2015，TRPO §5.2）；VinePPO（Kazemnejad 等 2024，arXiv:2410.01679） | 从轨迹上的状态复位，对多个动作做 rollout，用蒙特卡洛估值代替 critic；用公共随机数降方差。VinePPO 指出在稀疏奖励下 critic 的信用分配很差，改用中间状态的 MC 估值后明显变好 | **直接适用**：窗口少（每局约 4 个）、动作少（打 / 不打 / 换卡），复位便宜（0.13–0.4 ms）。我们的 critic 在窗口上的动作差只有约 0.005（PR #163、§7.4），正是 VinePPO 描述的情形 | 可用于评估回合 1 的终局面（D） |
| 组内基线：GRPO（Shao 等 2024，arXiv:2402.03300）、RLOO（Kool 等 2019；Ahmadian 等 2024） | 同一起点多条样本，用组内均值作基线 | A 的 K 个分支本身就是一个组：优势 = 本分支值 − π 加权的组均值 | **最合适**：同一手牌的 N 个回合 1 样本，按「对手线失败率」做组内相对优势（scaling.md T11 已把 GRPO 限定在回合 1 展开） |
| 反事实基线 COMA（Foerster 等 2018） | 固定其它因素，只把自己的动作边缘化，得到优势 | A 等于用模拟器做的 MC 版 COMA：对手线固定（脚本，确定性），只换本窗口的动作 | — |
| 公共随机数 PEGASUS（Ng & Jordan 2000） | 固定随机种子比较策略 | 分支之间共用学习者与快照对手的采样种子（`branch.try_all` 已经这么做） | 同一组 M 个对手手牌和种子评估所有候选 |
| 专家迭代 ExIt（Anthony 等 2017）、AlphaZero（Silver 等 2018） | 搜索出比策略更好的动作分布，再蒸馏回策略 | — | **适用但要改评估器**：回合 1 期间学习者的信息并不完全（对手手牌未知，对手可能在回合 1 打手坑）。评估要对对手手牌采样（PIMC）。策略融合（Frank & Basin 1998；Long 等 2010）的风险在于每个世界各自选最优；办法是**每个候选在全部 M 个对手样本上取平均后再选**，并且回合 2 的回应由真实策略来打（不用 oracle） |
| AWR（Peng 等 2019）、MPO（Abdolmaleki 等 2018） | 按优势指数加权做监督，再加 KL 信赖域 | — | D 的蒸馏形式。候选来自策略自己的支撑集，所以 KL 小，可以避开「BC 老师亏 13 pp」那种分布外目标 |
| 从演示或中间状态起局：Salimans & Chen 2018（arXiv:1812.03381）、Go-Explore（Ecoffet 等 2021）、反向课程（Florensa 等 2017） | 从靠近关键决策的状态开局，提高稀疏奖励的样本效率 | B 的依据：从「回合 2 开始」起局，样本全部落在回应窗口附近 | — |
| 基于势的塑形（Ng 等 1999） | — | 已试过，负效应（§6.4），本计划不再用 | — |

小结：窗口反事实就是 vine / COMA 式的 MC 优势，前提是对手在「被打断后」与「没被打断时」都打出合理的线。否则估出来的是「打断 × 对手变弱」的混合效应（§0 第 3 条）。

## 5. 设计

### 5.0 总体数据流

```
发局（selfplay._deal_lines）──► HostPool 槽位 ──► 学习者回合 1（正常采样，行进 PPO）
                                   │
                                   ├─(B) 可选：prefix 起局，直接从回合 2 开始（局面库：学习者近期的回合 1 局面 / 求解器局面）
                                   ▼
                       对手回合 2：LinePlayer 按线走（C：反应式线；T6：被打断后换恢复线）
                                   │ 学习者窗口（有打断候选）
                                   ├─(A) snapshot → 分支「打」→ 推演到回合 3 → V₁ → restore
                                   │      分支「不打」→ 推演到回合 3 → V₀ → restore → 走真实采样动作
                                   ▼
                       Rollout 行（branch_value[a] / branch_valid）──► PPOLearner.targets()：优势与 Q 目标
(D) 离线 / 每 64 次更新：同一手牌 N 个回合 1 候选 × M 个对手线 → 组内优势 → turn1_exit 数据集 → 加权 CE + KL
(E) 线库：诱饵在前、真起手在后的线（求解器约束 + fire 分级）→ 按份额发局
```

### 5.1 A：窗口反事实优势

**哪些窗口算数**：学习者的 `MSG_SELECT_CHAIN` 决策，满足三个条件：
(a) 至少一个非 pass 的可选候选（「打断候选」）；
(b) 在脚本线局的对手回合里：先手席位 `turn == 2`，后手席位 `turn == 1`；
(c) 按 `branch_fraction` 抽样（默认 1.0，即只要满足条件都分）。
自博弈局默认不分，因为对手不确定，CRN 只能部分配对；做成选项。

**分支集合**：`pass` 加上按 π 概率排前 `branch_k − 1` 的打断候选，默认 K = 2，即「打 π 最想打的那张」和「不打」。

**推演**：同槽位 `snapshot → step(候选) → 推进 → 停在视界 → 取值 → restore`，所有分支跑完后再走真实采样的动作。分支里：
- 学习者：当前模型，使用分支专用的 `torch.Generator`，种子 = hash(窗口 id, 推演号)，各候选共用（CRN）；
- 对手：`LinePlayer` 的状态在快照时 `copy.copy` 一份，恢复时还原。线没断时零网络开销；线断了，有恢复线（T6）就走恢复线，没有就由快照策略接手（用分支种子）；
- **视界**：学习者在回合 3 的第一个决策（先手）/ 回合 2 的第一个决策（后手），或对局结束。取值：学习者视角的 critic V（特权 critic，设计 I9），对局结束则取 ±1；
- 可选 `branch_rollouts M > 1`：每个候选推演 M 次取均值；
- 可选 `branch_opponent_best_of`：对手取 M 次里对学习者最不利的一次。这是没有恢复线时的替代，用来抵消快照策略恢复能力弱的偏差。

**写进 Rollout**：新增 `branch_value [T,B,A]`（未分支的格子填 NaN）和 `branch_valid [T,B]`。分支内的决策**不进训练行**。

**优势与 Q 目标**（`ppo.py`，与 VRPO 共存）：
- 对 `branch_valid` 行：Â = V_b(a_taken) − Σ_{a∈分支集} π̃(a)·V_b(a)，其中 π̃ 是 π 在分支集上的重新归一化（COMA 式基线）。
  - 如果真实动作不在分支集里（K < 候选数时可能发生），这一行的 Â 退回 VRPO。
- `branch_mode = "replace"`：用 Â 替换这一行的 VRPO 原始优势。
- `branch_mode = "add"`：原始优势加上 `branch_coef · Â`。
- 以上都发生在归一化之前，与 `line_bonus` 完全同一个位置（`PPOLearner.targets`）。

**代价估计**（128×128 一次更新 16,384 行；数字来自 §3 与 [benchmarks.md](../benchmarks.md)「收集循环」：学习者一行前向约 0.21 ms，快照对手一行约 0.85 ms）：

### 5.3 C：反应式对手

先说清楚现在的问题：先手脚本局里，线是按空场求解的。学习者的场面只在两种情况下有影响：先手容差匹配失败而断线（`broken`），或学习者真的发动了打断。断线后对手由快照策略接手，几乎展不开（§0 第 3 条）。
所以要的东西是：**对手在知道学习者场面之后（C1），以及被打断之后（C0），仍然走一条合格的线。**

两层方案：

- **C0 恢复线（便宜，先做，即 T6）**：
  - 灰流丽：被打断时，如果求解器 `--fire` 产出了该时点的恢复线（`variant="fire"`，按（线，时点）索引），`LinePlayer` 就切换到恢复线继续；没有恢复线，说明该时点就是「破场」，交给快照策略接手。这个结果本身是对的。
  - 其它打断（场上无效、陷阱）：没有现成的恢复线。离线批量对线库里每条线、每个学习者常见打断（按牌组统计的高频打断卡），用 `solve_fire --fire <密码>` 生成，同 #439 流程。代价约每条线 6–20 s，772 条线 × 3 张卡 ≈ 4–13 CPU 小时，可以夜间跑完。
- **C1 按学习者实际场面再求解（贵，异步）**：
  - **能力缺口**：求解器有 `--player <0|1>`（优化哪一方的回合）、`--start <replay>` 和 `--turns`（README 选项表），但「从一份含学习者回合 1 的 `.yrpX` 出发，替玩家 1 搜索回合 2」**没有验证过**（假设，T7a 先做 spike）。目标沿用该线在空场上的终场（子集匹配），所以求解结果回答的是「学习者的场面下，对手还能不能到达原来的终场」。搜索里学习者是被动的（求解器的对手只放弃连锁），学习者的打断仍由真实对局里的 `LinePlayer` 断线机制和 C0 处理。
  - **预算**：求解每手约 6 s（阻断目标，10 s 预算，§7.3b）到 45–60 s（spike 级预算）。不能在线同步跑。
  - **异步 + 缓存**：位置键 = hash(先手 `Replay` 的起始身份 + 回合 1 应答序列)，或者更粗一级的「场面键」= (对手线 id, 学习者场上 / 盖卡 / 墓地的卡片密码多重集合, 对手手牌)。
    - 求解服务 `ygorl.solver.service`：多进程，`nice 19`，有界队列，按键去重，结果写进 JSONL 缓存（续跑契约同 `solve_openings`）。
    - 训练侧在先手脚本局进入回合 2 时，按 `resolve_fraction` 把（局面、键）入队。
    - 命中缓存时对手改走反应式线，未命中走原线。另外，已求解的局面作为**前缀起局**（B）按 `reactive_share` 重新发出：学习者从回合 2 开始，只训练回应窗口。
  - **吞吐**：16 进程、10 s 预算 ≈ 1.6 次求解/秒，约每分钟 100 次；本机 128×128 大约 1 次更新/分钟，一次更新约 25 局先手脚本局，入队有余量。但它和环境工作线程争 CPU（本机已经满载），需要限核。
  - **更便宜的替代（C1'）**：不调求解器，在同槽位快照上对对手做「线库内选择」。同一个对手手牌有多条求解线（不同目标、恢复线），各试一次（每次约 6 ms 引擎时间 + 学习者前向），挑对学习者最不利的一条。这是对手侧的最优选择，不调求解器，成本 ≈ A 的一个窗口。
  - **对场面键命中率的依赖**：同一手牌下，学习者回合 1 场面的分布有多集中，P0c 会测。

**风险**：求解器搜索里学习者被动，搜出的线可能正好撞上学习者的速攻打断，于是又断。这没关系，断了就交给 C0。求解器的目标是「原终场」，不含「解场 / 斩杀」，所以对手在 C1 下可能比真实玩家保守（假设，接受）。

**T7a spike 结论（2026-10-24）：现有求解器（ygo-combo-solver `e0c7221` + 我们的补丁）不能做 C1，需要改求解器。**
做法：先手脚本局起局（`LineScript.spec(learner_seat=0)`），学习者用随机策略走完回合 1（至少 2 张场上卡），线的一方被动；停在玩家 1 回合 2 的第一个决策，导出 `.yrpX`（14–17 个应答）；
目标 = 该线 plain 记录的场上目标卡（子集匹配）。试了 5 条线（1 条的目标全在手牌 / 墓地，求解器拒绝；4 条有效）× 最多 4 种调用：`<t1.yrpX> --start <t1.yrpX> --no-ref --player 1 --target … --target-subset`，分别配 `--turns 1/2/3`；以及不带 `--start`、以该 `.yrpX` 为参考线。
脚本与日志在 `out/claude-scale/phase0/t7a/`（脚本不进 git）。结果：
- **`--start` 只取回放头部（卡组、种子、规则），丢掉全部应答**（源码注释原话：「Its stream and its answers are useless here: this is a starting position, not a line to follow」）。`--verbose` 轨迹证实：搜索从新开的对局起步，学习者回合 1 的每个决策都只剩 1 个选项（非目标玩家一律放弃，`KeepOnlyLast`），学习者场上是空的。也就是说，就算搜出线，搜的也不是学习者实际场面下的回合 2。
- **目标与搜索域写死为「目标玩家走回合 1」**：参考线的目标场面在第 2 次 `MSG_NEW_TURN` 时截取；搜索按从根开始的回合数截断，打分与目标检查只在回合 1 的场面上推进。`--player 1 --turns 2` 时求解器确实会走到玩家 1 回合 2 的主阶段（轨迹里能看到召唤、盖放等候选），但 4 条有效线全部 `0 of N target cards`，连「盖一张手里的 Majesty」这种 1 步目标都没记成解；`--turns 1/3` 同样 0 解。
- **不带 `--start` 的参考线模式不接受指定目标**（`--target` 需要 `--deck` 或 `--start`），而参考线自己截取的目标是玩家 1 在回合 1 结束时的空场面，没有意义。
- 耗时：每次调用在 20 s 预算下跑 15–16 s（4 线程）即放弃，没有解可以拿到核心里重放；重放验证环节因此无从谈起（脚本里已写好：前缀是否等于学习者回合 1 的应答、目标在第几回合达成）。
- **要让 C1 成立，求解器需要一个「固定前缀」入口**：例如 `--start-at <n>`，先在 `--start` 回放上执行前 n 个应答（学习者回合 1 与回合 2 抽卡），把这一点作为搜索根（arena 快照），回合计数、目标截取与「回合结束」判定都相对于根；探针、工作线程、finisher 共约 6 处新建对局的地方都要改成「建局 + 前缀」。量级是一个中等补丁（数百行），要随补丁队列维护，并补一条「前缀局面下回合 2 能到达目标」的端到端测试。
- 在补丁之前，C1 的替代是 C1'（同槽位快照上从线库里选对学习者最不利的线，不调求解器）。T7b 推迟到求解器补丁之后。

### 5.4 D：回合 1 专家迭代（ExIt）

- **起点**：学习者卡组 d、手牌种子 s（先手席位）。对手样本是 M 份（对手卡组、手牌、线）。默认 M = 8，从线库抽，所有候选共用（CRN）。
- **候选**：N 个回合 1 轨迹。用当前策略（温度 1）采样 N − 1 条；如果这手有求解器阻断线，加上它作为第 N 条（只当候选，不当目标）。
  - 实现：每手在一个槽位开局（对手用被动占位卡组），回合 1 起点拍快照，依次恢复、采样 N 次，记录每次的回合 1 动作序列（前缀）。
- **评估**：对手卡组和手牌在建局时就定了，**不同对手样本不能共享一个快照**。所以每个（候选 i，对手样本 m）都是一次前缀起局：用对手 m 的卡组建局，重放候选 i 的回合 1 动作（B，20–30 ms）。如果同一对局要推演多次（M 个随机种子），就在该槽位拍快照后依次恢复。总成本是 N·M 次重放 ≈ 16 × 8 × 25 ms ≈ 3.2 CPU 秒每手。
  - 前提：学习者回合 1 的动作序列与对手卡组、核心种子都无关。每条对手线都带着自己记录的核心种子；脚本线局开着 `DUEL_PSEUDO_SHUFFLE`，所以回合 1 里剩下的随机只有掷币、骰子和随机选择。另外，如果对手在回合 1 发动了手坑（例如灰流丽），前缀也会失配。这两种失配都从该对手样本的评估里剔除，失配率单独报告。失配率高（> 10%）就改成对每个对手样本重新采样候选，成本 ×M。
  - 对手按线走（C0 恢复线；有 C1 缓存就用 C1）；学习者用当前策略回应（不用 oracle），推演到回合 3 起点，或在线完成 / 断线后多走 `k` 步就截断；
  - 分数 J_i = mean_m [V(回合 3 起点) 或终局 ±1]，附带记录「对手线失败率」= 线没完成、或对手终场阻断点 / 攻击力和低于原终场的比例。
- **目标**：组内优势 Â_i = (J_i − mean J)/std J（GRPO 式），权重 w_i ∝ exp(Â_i/β)（AWR，β = 1）。只保留至少有一个候选 Â > 0.5 的手，避免把噪声蒸馏进去。
- **蒸馏**：把被选候选的回合 1 每一步写成（观测，动作，权重）数据集，`train/turn1_exit.py`（新增，仿照 `line_labels.ce_targets`）。在 PPO 里加 `turn1_exit_coef · Σ w·(−log π)`，加上已有的 KL 到 EMA 参考，只作用在回合 1 的行上（`prior_rows` 的同一套判别逻辑）。每 64 次更新用新 ckpt 重新生成一轮（迭代）。
- **成本**：2,000 手一轮 ≈ 2,000 × 3.2 s ≈ 1.8 CPU 小时的重放与引擎时间（16 核约 7 分钟）。学习者前向约 2,000 × 128 × 4 ≈ 100 万行 × 0.21 ms ≈ 3.5 GPU 分钟。线断后的对手前向用截断规避（断线后 `k = 0`，直接取 V）。
- **与已失败的 P-prior / BC 老师的区别**：
  - 目标来自策略自己的样本（支撑集内），所以 KL 小；
  - 打分看的是「对手线在学习者真实回应下是否失败」，不看件数；
  - 求解器阻断线只有赢了才会被选上。
  - 已知证据（PR #159、§7.3b）说明只看件数的目标会亏，所以 D 必须先过 P0d 的离线交叉验证门槛。

### 5.5 E：诱饵线库

- **现状**：留出手里只有 16 手「第 1 个时点是诱饵、动点在后」（§7.3b），训练线里这类线太少，「忍过诱饵」得不到压力。
- **生成**：
  - 对线库中每套牌，先用 `blocking` 的统计找出「可恢复的起手效果」：灰流丽标签里 u = 0 的时点对应的效果，例如 Maxx "C" 的 P(破场) = 0.07、Sky Striker Engage 0.12。
  - 再让求解器在保持原终场目标的前提下，加约束 `--resolve "<诱饵卡>:1"` 或 `--summon 1:<诱饵卡>`，使线先用这张卡开动。
  - 对产出的线跑 `solve_fire` 分级，**只保留**第 1 个灰流丽时点可恢复（打了白打）、后面某个时点打了就破场的线。
  - 成本与 C0 的离线批量同级（每条线 10–30 s）。
- **发局**：`--line-bait-share p`，按份额优先发诱饵线（`LineLibrary.dealable` 的加权版）。配合 C0 恢复线：在诱饵点开火 → 对手走恢复线 → 学习者吃亏；忍住 → 在动点开火 → 破场。A 再把这个差别变成逐窗口的信用。
- **风险**：求解器约束可能让线变长或解不出（预算放宽到 30 s）。诱饵线占比太高会教出「永远忍」（R3 曾出现过度忍住），所以份额从 0.25 开始，并且监控「漏打」。

### 11.2 方法

新工具 `tools/branch_adv_diagnosis.py`（冒烟测试 `tests/test_branch_adv_diagnosis.py`）：在 CPU 上 `Trainer.resume` LL u1088（它的卡组、两席位脚本线、联赛池、critic），
加 `recovery_full.jsonl`，按 A1n 的分支规则但 **fraction 1.0、M = 4** 收集 128×128 的段，每个窗口每个候选的 4 次推演值都单独留下（对收集器的几个方法打桩，不改 `rollout.py`）。
`--no-crn` 让同一推演号的两个候选用不同种子。同一段上：用第 1 次推演、随机一半窗口重建 A1n 的 Â（`branch_advantages`，`replace`，场面分 × 0.1），与该段的 VRPO 原始 / 标准化优势对比；
复制学习器做一次 PPO 更新（同一 minibatch 顺序）比较各种接法；再用别的检查点的 actor 给同一批窗口观测打分。
两次运行：CRN 3 段（800 个窗口，全部有效），无 CRN 2 段（510 个窗口）；8–16 核，机器负载 15–75，一段收集 90–330 s，一次 CPU 更新约 160 s。
「打更好 / 不打更好 / 平」都按 4 次推演均值 Δ = V(打) − V(不打) 的符号；π̃_f 是策略在分支集 {打, 不打} 上重新归一化的打的概率。

  与 P0b 对照：(i) 快照的判打率 0.755 是在灰流丽时点上，这里是所有打断窗口，判打 0.44 / 平 0.27；(ii) 恢复线在标签「不打」时点判不打 69%，这里有恢复线的窗口判不打 0.58，方向一致，但这类窗口只占 3%。

  M = 4 均值仍有 24% 的方差是噪声。提高 M 是 √M 级别的收益，分支内决策随 M 线性增长（全窗口 M = 4 时一段 43k–87k 个，约是 M = 1 的 4 倍）。

### 11.5 原因 3：主目标的反向压力

读法：
- **窗口行上主目标没有在奖励开火**：VRPO 在窗口行上与反事实不相关（一致率 0.47–0.53），critic 只有 25% 的窗口偏好打，开火局与不开火局的胜率和下游优势都没有差别。把窗口行的 VRPO 优势置零（11.6 的 `mask`）对更新几乎没影响。
- **但训练分布上开火率在两条臂里都涨了**：0.37 → CTRL 0.59 / A1n 0.51。这不来自窗口行的优势（上一条），而来自共享参数：其它行的更新把「在对手回合发动」整体抬高。

### 11.7 结论

按影响大小排序：
1. **信号本身方向不对（偏差 + 覆盖）**：A1n 不要求恢复线，64% 的窗口由快照接手，反事实净判「打」；真正能说「忍」的有恢复线的窗口只占 3%。#442 的「68% 说不打」是把平局（≈ 40%）算进了不打。
2. **幅度被 COMA 收缩吃掉，不是被标准化吃掉**：近确定窗口上 \|Â\| 是 \|Δ\| 的 1/20–1/60，分支行只占全段 Σ\|A\| 的 0.3%；单独缩放没有用。
3. **噪声大且 CRN 无效**：单窗口 M = 1 已决符号可靠性 0.70，平局 41–44%；M = 4 仍有 24% 噪声方差。
4. **主目标在窗口行上不构成反向压力**（VRPO 与反事实不相关，开火局不更赢）；训练分布上的开火率上升来自共享参数的整体漂移，两条臂都有。

## 13. 先手差的分解与前瞻对手（2026-10-27）

问题：扩展面板上先后手差 8–12 pp 从没收窄过（§6.4、§12）。P0d（回合 1 候选选择）与 PR #167（回合 2 时点）都说学习者的单点选择只有 +2 pp 左右的余量。
本节回答：(1) 差距落在哪一回合，是不是学习者的选择造成的；(2) 做一个会对学习者实际场面作反应的对手，给先手训练用。
代码：`ygorl.train.lookahead`（前瞻 = best-of-K 快照分叉；评估驱动 `play`；收集器接入 `Assignment.lookahead`）、`tools/seat_gap_decomposition.py`（分解实验）、`tools/lookahead_bench.py`（吞吐）；测试 `tests/test_lookahead.py`。
全部 CPU，`taskset` 限 16 核（两个作业各 8 核）；本机同时有 GPU 训练臂在跑，负载 20–25，耗时只作量级参考。结果 JSON 在本次 worktree 的 `la_out/`（不进 git）。

### 13.1 方法

- **学习者**：S3-A0 u2112。**对手**：(a) 强锚点 E2016 + G576，面板的 meta 卡组，100 个配对（种子 2026102701）× 2 个对手 × 学习者各持两个卡组槽 = 每席位 400 局；
  (b) 脚本线 `lines_train.jsonl`（747 条可用）+ 恢复线（`recovery_full` + 遮蔽者 `recovery_multi_97268402.pruned`，4,254 个（线，窗口，卡）），每席位 400 局，线断后由学习者 ckpt 接手（同 `first_seat_line_eval.py`）；
  (c) 镜像：对手 = 学习者自己（S3-A0 u2112），200 个配对，每席位 400 局，只跑 base 与 opp。
- **公共随机数**：每局一个键，主对局每个抽样决策用（键，席位，该席位第几个决策）的哈希，同一批局在各条件下逐局配对，直到第一个被改的选择。增量 = 逐局得分差的均值 ± 配对标准误。
- **前瞻（best-of-K）**：在符合条件的决策上从该席位策略抽 K = 8 个候选（第 1 个就是不前瞻时会走的那个，重复的去掉），同槽位快照，每个候选由双方原样（策略，或线 + 恢复线）推演到**本回合结束**（下一回合的第一个决策，或终局），按**前瞻分**取最高，恢复主对局走它；平分取靠前的（即策略自己的选择）。
  前瞻分（从决策方看，§10.2 的场面分）：自己回合的决策 = 己方场面分 − 对方场面分 + LP 差 / 1000；对方回合的决策 = −对方场面分 + LP 差 / 1000（打掉手坑不记为丢了阻断点）；终局 ±100。K = 1 与原策略逐位相同（测试）。
- **推演看得到全部引擎状态**（对手手牌、双方卡组顺序）。所以这是开天眼的上界，不是可部署的搜索；它测的是「把这一段的单点选择换成 best-of-8 最多能赚多少」，与 #167、P0d 的 oracle 同一口径。
- **段**按回合号切：先手 t1 = 自己回合 1 布阵；t2 = 对手回合 2 里学习者的全部决策（手坑、场上效果的连锁窗口及后续选择）；t3 = 回合 3 起全部决策；all = 全部。后手 t1 = 对手回合 1 里的回应；t2 = 自己回合 2 的展开与进攻；t3、all 同上。
- **opp**：只给对手在它自己的第一个回合（学习者先手 → 回合 2；后手 → 回合 1）做前瞻，学习者原样。

### 13.3 读法与结论：8 pp 在哪

1. **差距是席位本身，不是学习者比对手差在哪个选择上。** 镜像（双方同一个策略）里先手方只赢 0.427 / 0.407（两批局），学习者先后手差 16.6 pp；学习者对强锚点的差是 14.1 pp（0.562 对 0.703）。面板上的 8–9 pp 是被弱对手（先后手都 0.84 以上）摊薄后的数。在当前人群与 MD 规则下，后攻多一张牌、先进攻，而先手回合 1 的场面挡不住：
   回合 4 结束前，先手已经输掉 20% 的局、只赢 14%；后手已经赢下 44%、只输 3%。**差距集中在回合 2–4，也就是后手的头两个进攻回合。**
2. **学习者在对手回合 2 的回应没有余量**：先手 t2 = 0.0 ± 1.4（强锚点）/ +1.2 ± 1.2（线），开天眼的 best-of-8 也只改了每局 0.5–0.7 个选择。这与 #167（+2 pp）、§12（反事实 CE 改时机但不涨胜率）一致：手坑与场上效果的打法不是差距的来源。
3. **回合 1 布阵有小余量，只对策略对手**：先手 t1 = +4.8 ± 2.4（强锚点；视界放到对手回合后 +6.0），对脚本线 −0.2。按场面分挑布阵能挡掉一部分回合 2 斩杀（回合 2 输 3.5% → 1.8%，回合 3 赢 12.5% → 17.5%），但远不够 14 pp；对按线走的对手没用（线不看学习者场面），与 P0d 的 +2.6 一致。
4. **大余量在进攻回合，而且两个席位都有**：先手 t3 +10.2 / +9.8，后手 t2 +7.0 / +11.5、t3 +7.5 / +11.8。先手 t3 的增益一半来自回合 3 斩杀（回合 3 赢 12.5% → 24.5%）：学习者经常漏掉斩杀线。这是普遍棋力（P0，#83），不是先手专项；全部替换后差距只从 14.1 缩到 10.2 pp（强锚点），线对手上反而从 1.5 拉大到 9.2。
5. **「对手会反应」只伤先手**：强锚点在自己第一个回合做前瞻，学习者先手 −12.0 ± 2.5，后手 +0.0 ± 2.3；镜像 −10.5 对 −3.0。先手多输的几乎都在回合 2、4（回合 2 斩杀 3.5% → 10.5%）。
   也就是：对手回合 2 是有进攻权的回合，那里的单点选择值 10 pp 以上；当前人群在那里留着这 10 pp 没拿，学习者的先手胜率是靠对手回合 2 打得不好撑着的，回合 1 的场面从来没被「会找斩杀 / 破场线的回合 2」检验过。对手回合 1（不能攻击）做前瞻对后手没有影响。
6. **结论**：8 pp（对强锚点 14 pp）不在学习者的哪一个单点选择里（回应 0、布阵 +5、两个席位的进攻余量相同），而在**席位**：后攻的头两个进攻回合。可训练的部分只有两块：
   (a) 两个席位都有的进攻回合余量（斩杀 / 进攻线，+7–12 pp 上界）——涨强度，但不缩差；
   (b) 先手回合 1 的场面对「会利用回合 2 的对手」的韧性——现有对手不施加这个压力，所以要换对手（§13.4 的前瞻对手）。现在面对前瞻对手，先手胜率 0.443，比面对原样对手低 12 pp，这就是先手训练的尺子。

### 13.4 前瞻对手原型

**接口**（`ygorl.train.lookahead`）：
- `LookaheadConfig(k=8, rollouts=1, first_turn, last_turn, own_turn, own_weight=None, lp_scale=1.0, win_value=100, candidates="sample"|"top", extra_turns=0)`；`applies(obs)` 判断一个决策是否前瞻（回合范围、自己 / 对方回合、≥ 2 个可选行）。
- `look_ahead(cfg, seat, n, ev, probs, draws, hooks, score)` 是生成器：产出环境请求（`forward` / `step` / `snapshot` / `restore` / `release`），返回 `(动作, info)`。所以任何按槽位批量前向的驱动都能跑它：
  - 评估：`play(env, games)`，`GameSetup(spec, (SeatPlayer(module, lookahead), …), key, line=…)`，所有槽位的前向按模块合批；脚本线座位走 `LineHooks`（线状态与窗口计数随快照保存 / 恢复，学习者的发动照常切恢复线）。`tools/seat_gap_decomposition.py` 与 `first_seat_line_eval.py` 同口径（先手对线 / 对前瞻对手）。
  - 自博弈：`Assignment.lookahead`；`SelfPlaySchedule(lookahead=cfg, lookahead_share=p, lookahead_second=False)` 在非脚本的池对局里按份额给快照对手挂上前瞻（学习者先手那局是回合 2，`lookahead_second` 时后手那局的回合 1 也做）；
    `RolloutCollector._look_round` 驱动生成器：对手座位用快照、学习者座位用当前模型推演（不记行），这类槽位记入 `_branching`（锁步收集同样暂停其它槽位）；`Rollout.lookahead_*` 与 `metrics.jsonl` 计数。
    训练器：`--lookahead-share / --lookahead-k / --lookahead-rollouts / --lookahead-second`（需要 `privileged_critic`，环境自动开 `snapshots`）。没有跑训练，只有冒烟测试。
- 分叉不改主对局：恢复后的观测与快照时逐字节相同，主对局的随机数不被推演消耗；测试：K = 1 与原策略逐位相同、同键同局两次相同（不同槽位数 / 批次）、快照全部释放、人工局面（回合 1、手里全是 4 星通常怪、策略 80% 以上直接结束回合）里前瞻选召唤（场面分 1 对 0）、收集器冒烟（`lookahead_share 1`，有前瞻决策、无快照残留、学习者行数不变）。
- 没做：critic 混合评分（§10.2：回合起点的 critic 分不出展开成败，`lookahead_value` 只用场面分 + LP；要加就在 `score` 回调里加）；推演不开天眼（需要对隐藏信息做确定化，快照做不到）。

**吞吐**（强锚点 opp 条件，K = 8，`candidates="sample"`）：先手局里对手回合 2 每局约 38 个符合条件的决策，其中 17.4 个有 ≥ 2 个不同候选、真正分叉；每个分叉决策在推演里走 89 个引擎决策（全部候选合计），每局多 1,500 次前向行（原来整局 164 行），约 4 个选择被改。
`tools/lookahead_bench.py`（学习者先手对 G576，256 局，128 槽、16 个引擎线程、8 个 torch 线程，负载 27–58）：

| | 每局墙钟 | 每局前向行 | 每局符合条件 / 分叉 / 改动的决策 | 每个分叉决策的推演步 | 每个分叉决策多花的墙钟（128 槽摊销） |
|---|---:|---:|---|---:|---:|
| 原样对手 | 0.30 s | 163 | — | — | — |
| 前瞻对手 K = 8 | 2.80 s（×9.4） | 1,562 | 39.6 / 18.2 / 3.9 | 80 | **0.137 s** |
| 前瞻对手 K = 4 | （负载 70–180，墙钟不可比） | 1,215 | 39.6 / 15.2 / 3.2 | 72 | — |

同一批局上学习者先手得分：原样对手 0.531，K = 4 前瞻 0.484（−4.7 pp），K = 8 前瞻 0.449（−8.2 pp；单批 256 局，未配标准误）。K = 4 只省 22% 的前向（候选本来就是策略样本、重复多），对手却弱了一半，所以训练用 K = 8。
时间 88% 花在 CPU 前向上（8 线程约 640 行 / 秒），引擎推演不是瓶颈。训练里前向在 GPU 上（§5.1 的估计：快照对手一行约 0.85 ms、学习者约 0.21 ms），一局前瞻多约 1,400 行 ≈ 1 s GPU 时间；
按 13.5 的配比每次更新（128×128 约 100 局）有约 12 局前瞻局，收集多约 10–15 s（对约 30 s 的整步 +30–50%，估计，未在 GPU 上实测）。负载 140–330 时（另一会话）同一基准每个分叉决策 0.51 s，前向被挤占时开销放大很多。

**实测与优化（2026-10-27，阶段 4 的 LA 臂）**：上面的 +30–50% 估计错了。LA 臂第一次更新 67 rows/s，对照 LA-CTRL 290 rows/s（4.3 倍），之后掉到 38 rows/s。
原因不是前向算得慢，而是**前瞻是一条很长的串行往返链**：推演里每一步都要等一次前向，而收集器里一个槽位一轮只能走一步。

- **剖析**（`tools/lookahead_bench.py --collect`，LA 臂配置去掉脚本线、`--lookahead-share 0.5` 使前瞻局占比同为 12.5%，池里 8 个快照，GPU bf16、`YGORL_GPU_FRACTION=0.15`，与两条训练臂共用 GPU）：
  一次收集（16,384 行）约 1,000–1,300 个前瞻决策、450–630 个分叉、32k–58k 个推演决策；每个分叉决策平均 2.9 个不同候选、每个候选推演约 26 步到回合结束。
  原实现候选在同一槽位依次推演，一个分叉决策的链长 ≈ 候选数 × 26 + 快照 / 恢复 ≈ 80 轮；一个前瞻回合（约 45 个决策、21 个分叉）≈ 1,700 轮，长回合（对手回合 2 有 100+ 个决策，推演长度按决策数二次增长）一个槽位要 3,000 轮以上。
  而一轮（`recv` 64 个事件 + 学习者整模型前向 + 每个出场快照一次前向 + 前瞻前向）在共用 GPU 上要 25–45 ms：前向时间几乎全是 kernel 启动与 GPU 排队（`.cpu()` 等待 63 s / `linear` 启动 22 s，cProfile），批大小 1 与 128 的单次前向只差 2–3 倍。
  所以其余槽位早就收满 128 行，最后几个前瞻槽位独自走完上千轮（原实现：持有 100 个槽位时 100 s，最后一个槽位到 327 s）。引擎步、快照 / 恢复（< 1 ms）与 Python 往返都不是瓶颈。
- **优化**（选择逐位不变，见下）：
  1. **分叉槽位（`Forks`）**：环境多开 `lookahead_forks`（默认 64）个备用槽位；一局第一次分叉时从备用槽位取至多 K − 1 个，用前缀起局（`reset(spec, prefix=动作序列)`）重放到当前决策（一次约 47 ms 引擎线程时间，几乎全是建局与加载脚本），之后逐个动作跟随主对局，到下一个决策时不必再重放；前瞻回合结束或终局时归还。
     一个决策的候选分给主槽位与这些分叉同时推演（`look_ahead(runners=…)`：第 r 个跑候选 r, r + R, …，各自快照、推演、恢复；推演用的随机数只取决于（局，决策，候选，第几次推演），与在哪个槽位跑无关），链长从「候选之和」变成「最长的候选」。借出前核对分叉的观测与主对局逐字节相同，不同就报错。
  2. **前向合批**：前瞻的快照前向并入同一轮该快照的主前向，学习者座位的前向并入学习者的前向（原来每轮另起两次前向）。
  3. **只走前瞻的轮次**（异步收集，`lookahead_rounds`，默认 4）：主对局的事件不够 `min_batch` 时，不等它们，先让前瞻局（运行中的前瞻、它们的分叉、处在前瞻回合里的前瞻局）单独走一轮，其余事件留到下一轮；两个整轮之间至多 4 个这样的轮次，其余槽位都已收齐时不限。
  候选去重本来就有（重复抽样只推演一次）；推演视界已是「回合结束（下一回合的第一个决策）」，没有多推。`candidates="top"` 每个分叉决策固定推演 min(K, 合法行数) 个候选（`"sample"` 平均 2.9 个）：有分叉后链长只取决于最长的候选，但分叉、重放与前向行数约是 2–3 倍；本次没有测它的吞吐。
- **结果**（同一进程里先测原样对手，再测前瞻对手；本机负载 10–80，单次收集波动 ±30%）：

| | 原样对手（收集秒） | 前瞻对手（收集秒） | 倍数 |
|---|---:|---:|---:|
| 原实现（f73afa2） | 71.0 | 361.6 | ×5.1 |
| 本次（分叉 64 + 合批 + 前瞻轮次，引擎线程 2） | 72.7 | 133.5 | ×1.84 |
| 同上，引擎线程 4 | 55.8 | 119.1 | ×2.1 |

  前瞻臂的收集提速约 2.7 倍；**没有达到 ≤ 1.5 倍对照的目标**。剩下的时间几乎都在最后一两个槽位的长前瞻回合上（最长的槽位约 1,700 轮，尾部每轮约 30 ms），这是「推演到回合结束、每步一次 GPU 前向」本身的串行深度，等价优化压不下去了。
  评估驱动（`play(forks=…)`，CPU）：96 局学习者先手对 G576，96 槽、8 引擎线程、8 torch 线程：原样对手 0.25 s / 局，前瞻单槽位 2.33 s / 局（14,399 次前向调用），带 64 个分叉 1.91 s / 局（11,736 次，212 次重放），对局与选择逐位相同（工具里断言）。CPU 上前向是按行计算的（每局 1,470 行），分叉只省调用次数，所以只快 18%；收益在 GPU（延迟受限）上。
- **等价性**（`tests/test_lookahead.py`）：(a) 锁步收集（与批次无关的策略）的行、对局结果与前瞻计数的摘要，与 f73afa2 上同一配置记下的摘要逐位相同——不开前瞻、前瞻在单槽位、前瞻带分叉（K = 4 / 8）；(b) 异步收集（分叉 + 前瞻轮次）与锁步单槽位收集在「学习者选择确定、对手每个决策都前瞻」的设置下逐局相同（所以每个前瞻选择相同）；(c) `play` 带分叉（含分叉不够、槽位复用）与不带分叉的对局、选择与推演计数相同；快照全部释放、arena 无逃逸。

### 13.5 训练方案建议

- **起点**：S3-A0 u2112（当前最强；阶段 3 的 CE2 臂面板代价 −3.4 pp，不用）。
- **臂**（本机 128×128，各 512 次更新，≥ 2 个种子）：
  - **LA-CTRL**：S3-A0 配方（两席位线、恢复线、`selfplay_fraction 0.5`）但 `line_share 0.5`（让一半池对局不走线），不开前瞻——与 LA 的发局结构相同；
  - **LA**：同上 + `--lookahead-share 1.0`（K = 8）：池对局的一半不走线，其中学习者先手那局的对手在回合 2 做前瞻（约 12% 的对局）。前瞻局的前向约是普通局的 10 倍，收集估计 +30–50%（13.4）；嫌贵就把 `lookahead_share` 降到 0.5，不要降 K（K = 4 省得少、弱得多）；
  - 可选 **LA2**：再加 `--lookahead-second`（后手局对手回合 1 也前瞻），检验 13.2 里「对后手无影响」在训练里是否也成立。
- **尺子**（每 64 次更新）：
  1. **R-LA**：`seat_gap_decomposition.py --class anchors --conditions base opp --seats 0 1`（强锚点，400 局 / 席位，CRN）。现在先手对前瞻锚点 0.443、opp 降幅 −12.0 pp。验收：先手对前瞻锚点 ≥ 0.50，且 opp 降幅收到 −6 pp 以内；后手对前瞻锚点不降；
  2. 扩展面板：先手胜率、先后手差、强锚点不低于 LA-CTRL −1 pp；
  3. 镜像先手胜率（同一工具，`--opponent SELF=`；现在 0.427）只作参考：它被席位本身限制，不设门槛；
  4. 留出手 R1（回合 1 打断数）与回合 2 斩杀率（13.2 第二张表的「对手第一个进攻回合赢下的份额」）作诊断。
- **另一条线（强度，不缩差）**：进攻回合的 best-of-8 余量 +7–12 pp（两席位）是本轮看到的最大单点余量，一半是漏掉的斩杀。建议先做两个便宜的检查再决定是否做回合级 ExIt：
  (a) 不开天眼的上界——同样的前瞻，但推演里对手的手牌 / 盖卡按公开信息重新抽（需要确定化工具，快照之外另做）；(b) 现成的 `lethal:` 包装（`agents/lethal.py`）在 C++ 评估路径上的增益。若 (a) 仍有 ≥ +5 pp，就按 D（§5.4）的蒸馏框架做「进攻回合 ExIt」。

### 13.6 遗留

- 前瞻开天眼：所有增量是上界；对手前瞻的 −12 pp 也是「会作弊的对手」造成的。训练用它没问题（它的作用是施压），但不能把 R-LA 当作对真实玩家的预测。
- `candidates="sample"`：候选来自策略本身，策略很确定的决策只有 1–2 个不同候选（先手 t2 每局 7 个符合条件、3.6 个分叉）。`"top"`（策略样本 + 概率最高的其它动作补足到 K）已实现，未跑分解；它会让前瞻对手更强，也更贵。
- 每个条件只有一个 400 局批次、一个学习者 ckpt；单点 ±2–2.5 pp。
- 第一次分解运行的强锚点局没有洗牌（`pairing_slots` 收到了关掉洗牌的配置），整批作废重跑；工具已改为先按槽位洗牌再关掉引擎洗牌（与面板的 `cell_specs` 相同）。
- 前瞻臂收集仍是原样对手的约 2 倍（目标 ≤ 1.5 倍，§13.4「实测与优化」）：剩下的是长前瞻回合的串行深度（推演到回合结束、每步一次 GPU 前向）。再快要改语义：推演步数上限（现在 600）、只在回合前若干个决策前瞻、前瞻局固定用一个快照（每轮少几次前向），或把 `lookahead_share` 降到 0.5；也可以让 LA 臂开 `overlap_collect` 把收集与更新重叠。
- 收集器接入有冒烟与等价性测试（§13.4），没有跑过完整训练；`lookahead_share > 0` 时 `Rollout.decisions` 不计推演里的步，吞吐日志里的「决策 / 秒」会低估实际引擎负载。

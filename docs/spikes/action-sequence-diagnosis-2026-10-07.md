# 检索发动前决策与事后补救（2026-10-07，#218）

用户指出：Lycoris 致死检索例中，更应避免发动检索，而不是教模型先犯错再自灰。
本轮原生分支验证支持这个判断。先清场再检索保留 Ash 且得到检索卡；
先检索、自灰、再清场则损失 Ash 且没有检索收益。对方回合不发动可以保留两张卡、避免当下的致死伤害。
前轮反例应归类为**前序错误后的补救测试**，不能作为主动进入该局面的示范。

对方回合发动/pass 也多受 200 伤害，但均不立即败北。所有 14 条分支及健康检查通过。

### 低 LP 脚本续局：存活不等于改善胜负

看完以上局部结果后，另在 `continuations/protocol.json` 登记终局检查，未重选模型或重写第一阶段协议。
精确重放七条低 LP 分支至已记录终点，随后己方尝试通常召唤 Warwolf、进入战斗并攻击；
对方只放行并结束阶段，其余窗口按固定 pass/yes/首个合法选择推进。不再发动额外可选法术或连锁。

- 己方回合：先检索/pass 在 T2 输；自灰补救再清场、先清场再检索、清场不检索均沿该脚本在 T2 赢。
  所以该低 LP 终局未显示后两者相对补救路线有胜率优势，只显示更好的资源保留。
- 对方回合：检索/pass 在 T2 输；自灰或不发动都在下一次 T3 抽卡受到 Lycoris 的 200 伤害而输。
  这两条线在此脚本下仅延缓败北。不能把这组“避免立即败北”标签当作已验证的胜负价值提升。

七条续局均健康、自然胜负终止；工件位于 `continuations/{identity,report}.json` 及各路线记录。
这是固定脚本的存在性/局限检查，不是原策略完整执行，也未枚举所有可能续局，不能证明对方回合状态必败。
该结果进一步要求后果教师区分即刻存活、资源偏好和整局胜负证据。

## 原策略在两个决策点的表现

| 时机 / 发动前己方 LP | 立即发动 Chant | 立即雷击 | 不响应 | 被推进检索后 P(自灰) |
|---|---:|---:|---:|---:|
| 己方回合 / 200 | 0.2706% | 0.0793% | 无此候选 | 4.0634% |
| 己方回合 / 7800 | 0.6131% | 0.1915% | 无此候选 | 4.7985% |
| 对方回合 / 200 | 34.6070% | 无此候选 | 65.3930% | 2.8533% |
| 对方回合 / 8000 | 37.3760% | 无此候选 | 62.6240% | 3.4664% |

己方低 LP 的首选是通常召唤 Gene-Warped Warwolf（58.19%），另一普通怪兽 38.49%。
因此“立即致死检索”在这个主阶段窗口只有 0.27%，不能把被强制推进后的自灰概率当成它经常主动犯该错的证据。
召唤之后是否仍会误检索，本轮未执行该策略路线，不能从这张表推出模型整条线路正确。

对方回合则有更明确的前序问题：低 LP 仍有 34.61% 概率发动检索；
在被脚本推进的后续响应窗口，97.15% 概率 pass 导致立即败北。
两处之间还有效果选项等脚本应答，未评估其全部策略分布，**不将两数相乘称为自然败率或完整策略路径概率**。

另一个诊断：己方先清场再检索后，P(自灰) 为低/高 LP **20.96% / 20.52%**；
此时检索不会再触发 Lycoris 伤害。这说明当前策略的自灰概率不能直接解释为“知道要规避致死后果”。
清场同时改变了场面和历史，不能把这个差异归因于某个唯一表示或损失机制。

## 实现、审计与复现

新增 `tools/action_sequence_probe.py`，复用既有 fixture 的卡组和原生数据读取，保持 Python/native mirror 同步。
保存完整输入、合法候选、脚本动作、事件、终点与关键卡位置。位置摘要只用于此唯一关键卡构成的 fixture；
它不是支持所有卡片移动/控制权变化的通用后果标注器。

首次 native-only 预检暴露一个检查假设：立即败北可能发生在结算中，Chant 尚未送墓。
保存失败和驱动于 `preflight-1/`，改为仅对非终局检查结算后送墓；模型尚未评分。
`preflight-2/` 全部通过后冻结驱动，正式评分及分支文件写入实验根目录。

独立 `audit.py` / `audit.json` 核对 14 条分支 SHA、健康状态、同前缀/同发动前输入、终点、分布归一化，
并从原生 Move 事件确认存活己方分支确实清除 Lycoris。
所有正式分支与成功预检逐字节相同；先检索路线的响应输入与上一轮反例逐元素相同。
`identity.json` 绑定来源模型、驱动、复用 fixture、协议、原生库与环境；结果为 `report.json`。

在新目录复制协议，然后从仓库根目录运行：

```sh
PYTHONPATH=src YGORL_THIRD_PARTY=/path/to/third_party OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  uv run --no-sync python tools/action_sequence_probe.py --output /path/to/new-sequence-run
```

添加 `--native-only` 可先核验分支而不评分；每个输出目录拒绝复用已有 identity。
协议中的来源路径需要对应本地已核验检查点。所有执行均为 CPU 诊断，没有启动新训练任务。

验证：`tools/presubmit.sh --test` 在沙箱内为 **1510 passed / 17 skipped，338.20秒**；
其中14项因GPU不可见而跳过，随后在本机ROCm GPU全部补跑通过（两次选择共15通过，含1个CPU重复项）。
剩余3项为未启用snapshot支持及2个需显式开启的网络检查。格式/lint通过。
原生14条分支和另7条终局续接单独通过，不将它们混入单测计数。

## 后续优先级

先收集真实策略前缀中的发动前错误，再以引擎分支后果构建跨效果族监督。
把“避免造成坏局面”和“在坏局面中补救”分别标注，保留未知及停止条件；
不能以单独降低自灰率验收，也不能只记住 Chant/Lycoris 组合。

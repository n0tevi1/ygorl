# Master Duel 集成：数据对齐与只读建议器

> 属于 [ygorl 设计文档](README.md)。状态：草案（2026-09-24；2026-10-21 增加「单人模式自动对局」），属于首期之后的扩展（见 [06-architecture.md](06-architecture.md) §5.2「对局接口」）。

## 定位与边界

目标：让训练好的策略在 Master Duel（MD）的真实对局里使用，形态是**只读建议器**（advisor）。它读取局面，在终端给出候选动作及其概率，由人自己决定是否照做。这是研究原型，用来衡量策略在真实对局分布上的表现，**不是 bot**：

- 不向游戏发送任何输入：不模拟点击，不注入按键，不调用游戏函数。唯一的例外是下文「单人模式自动对局」，
  它是单独的、需要显式开启的工具，只在对手是电脑时动作。
- 不往游戏进程写内存，不注入 DLL，不 hook。
- 不抓包，不改网络协议。
- 状态来源只有两种：手写或保存下来的盘面快照，以及从游戏进程外部**只读**读取内存（与 Untapped.gg Companion 同类）。

Konami《使用条款》第 3 节禁止自动化软件、bot、未授权第三方软件和逆向工程，所以读取器即便只读也有账号风险，见 [08-risks.md](08-risks.md)。开发与验证优先在单人模式（Solo）里进行。

## 单人模式自动对局（Solo 自博弈，草案）

用户 2026-10-21 决定：在单人模式里让策略自己打 MD，用来在真实 MD 规则与真实电脑对手上评估策略、积累对局数据。
用户知情并接受账号风险（Konami《使用条款》第 3 节明确禁止自动化软件和 bot，这一项比只读读取器风险更高）。边界：

- **只在对手是电脑时动作，失败即停（fail-closed）。** 每个决策前读 `duel.dll` 的玩家类型（`DLL_DuelIsHuman` 读的
  `K + 8 + p × 4`：0 = 人，单人模式里电脑为 1）：对手类型不是已核对过的电脑值、读不到、或 `duel.dll` 的偏移未核对，
  就不发送任何输入并退出。PvP（排位、活动、好友对战）永远不会动作。
- **输入只走操作系统层的模拟输入**，作用在游戏窗口上，与人用鼠标点击等价；仍然不写游戏内存、不注入 DLL、不 hook、不碰网络。
- **状态来源与建议器相同**：只读读取 → `BoardSnapshot` → 重建 → 策略。动作只从建议方可见的信息里选，与人打时一样。
- **动作 → 点击**：把重建里的 `Action` 映射成画面上的点击序列（选卡 → 选命令 → 选目标 / 区域 / 确认）。
  每次点击后重新读内存，确认局面按预期变化，不符就停，不盲点。
- 需要显式开启（单独运行 `python -m ygorl.selfplay.loop`），默认关闭；建议器 `ygorl advise` 本身仍然只读。
- 记录每局：快照序列、所选动作、结果，作为「真实 MD 规则下的评估」数据，绑定环境版本。

### 自博弈的架构：MD 管状态，ygopro 管规则与决策

**目标。** 规则基本一致，所以同一局面下 MD 给出的选项应当与 ygopro 的动作列表相同；UI 与结算动画不同只是「怎么点」的问题。
自博弈因此不为每种界面写决策规则，而是：**从 MD 读出状态与它正在问的问题，映射到 ygopro 的决策点，由策略在 ygopro 的选项里选，
再把选中的选项点出来。** 两边的选项集对不上的地方，就是重建的失真或真正的规则差异，记录下来，而不是猜。

**可行性检验（2026-10-21，单人模式，阿尔卡纳骑士小丑卡组）。** 在 MD 发动「王牌融合」之前的局面重建进 ygopro，走同一条线，
逐个决策点对照：

| 步骤 | ygopro | MD |
|------|--------|----|
| 发动「王牌融合」 | `SelectPlace`（5 个魔陷格子） | 选格子 ✓ |
| 对手的连锁窗口 | `SelectChain`：「堕天使与圣天使」或放弃 | 无。这张卡是给对手暗牌采样出来的，并不存在 ✗ |
| 自己的连锁窗口 | `SelectChain`：只有放弃 | 无（只有一个选项时 MD 不问） |
| 融合怪兽 | `SelectCard` 3 张「阿尔卡纳骑士小丑」选 1 | 列表 ✓ |
| 融合素材 | `SelectUnselectCard` {卡组「王后骑士」×3、手牌「卫兵骑士」、场上「国王骑士」} 选 3 | 逐张问：卫兵骑士、国王骑士；卡组的王后骑士自动补上 ✓（同一集合，问法不同） |

结论：**自己一方的动作，两边问的问题与候选一致**；差异有规律：(1) MD 跳过只有一个选项的决策，多选进行到一半时剩下的选项全等（同名同位置）也自动补齐；新的决策即使选项全等也照问（3 张同名融合怪兽）；
(2) 多选在 MD 里逐张问；(3) ygopro 会让**对手**用采样出来的暗牌做出 MD 里不存在的应对。同一局里还出现了第二类差异：
ygopro 让「小丑骑士」攻击，MD 不给攻击命令（多半是「王牌融合」发动后本回合只有融合怪兽能攻击，这类持续到回合结束的效果
不在快照里）。

**MD 的「问题」可以从内存读出来，不必看图猜。** 引擎的输入状态（`S + 0x3cd0` 模式、`+0x3cdc` 是否在等、`+0x3d00` 等谁）
说明在等哪一类输入；选卡列表在 `[duel.dll + 0x11f9c30]`（`DLL_DuelList*` 读的结构：头部 `+0x1` 最多选几张、`+0x2` 列表种类、
`+0xa` 张数，`+0x1a` 起每项 4 字节的 uid 字，`+0x4c8` 起每项来源位置），已在王牌融合的素材列表上核对；对话框（是 / 否、
表示形式掩码 `S + 0x3cb8` 等）由 `DLL_DuelDlg*` 读。偏移同其它字段一样从导出函数推导。列表里只有给建议方选的卡，
本来就在画面上，不涉及暗牌。

**组件。**

```
MD 进程 ─► md.memory  局面（BoardSnapshot）
        └► md.request MD 在问什么：种类、候选（uid → password + 位置）、选几张          ─┐
                                                                                        ├─► bridge：MD 请求 ↔ ygopro 决策点
ygopro 影子对局 ◄── 在命令点从快照重建；在自己的一个动作之内与 MD 同步前进            ─┘     对齐选项集、记录不一致
策略 ◄── ygopro 的观测与动作列表（遮住 MD 不允许的）                                         │
mdui  ◄── 「选第 k 个选项」→ 点击（布局、图标检测；不做任何决策）                        ◄───┘
trace ◄── 每一步：MD 请求、ygopro 选项、选择、点击、之后的局面
```

- **命令点**（自己回合的主要阶段 / 战斗阶段命令）：从快照重建影子对局（同现在的建议器）。
- **自己动作之内**：影子对局与 MD 同步：用同一个选择推进影子对局，到下一个决策点时与 MD 读出的请求对齐。
  - 影子对局里只有一个可选项（取消、取消选择不算）、或多选进行中剩下的选项全等的决策，自动回答（MD 不问）；命令点总是问。
  - 影子对局里**对手**的决策一律放弃 / 不应对；对手真的应对了，MD 的局面会与影子对局不同（下一条）。
  - 多选：MD 逐张问，桥逐张把影子对局的选择喂进去。
- **重新同步**：MD 是状态的权威，ygopro 是合法性与决策的权威。影子对局与 MD 读出的局面不一致（对手应对、抽到的卡、
  检索到的卡、掷硬币）时，在下一个命令点从 MD 重建；动作之内对不上时，当前这一步改用 MD 自己的选项集（列表候选与
  ygopro 动作按 password + 位置对应；对不上的选项不选），这一步记为不一致。
- **对手回合里问到自己**（连锁、发动时点）：无法在连锁中途重建，影子对局不参与；按 MD 读出的候选集决策（先用规则，
  之后接策略对单步选项的打分）。
- **选项集不一致是数据，不是故障**：每一条记录 MD 请求、ygopro 决策、差集，按原因归类（采样的暗牌、本回合效果、
  一回合一次、MD 合并 / 跳过、规则差异）。已确定的原因进遮罩（如「本回合盖放的陷阱不能发动」「已攻击过」），
  其余的进「重建的已知失真」一节。

**重建能还原什么、不能还原什么。** 能：场上 / 手牌 / 墓地 / 除外 / 卡组构成、LP、表示形式、超量素材、本回合召唤与盖放与
改变表示形式的标记（槽位 `+0x14`）、通常召唤次数、阶段。不能（目前）：一回合一次的已用记录、持续到回合结束的效果
（上面的攻击限制）、装备 / 指示物以外的效果附带状态、连锁中途的局面、对手的暗牌（采样，因此对手的决策不可信）。
前几项在 `duel.dll` 的效果链表里（`S + 0x2bec` 的节点，种类与代码已能读出），是继续解码的方向；解码之前由「MD 不给这个命令」
的信号兜底：MD 的命令图标就是它对这张卡的命令掩码，没有对应图标的动作视为被 MD 禁止，遮住后重新决策。

**指标**（每局的 trace 汇总）：选项集一致率（按决策种类）、策略意图达成率（动作后的局面检查）、卡住次数与原因、
需要回退到规则的步数。目标是只靠脚本跑完整局：卡住为 0，回退步数逐局下降。

**迁移步骤**（每步单独可用）：
1. `md.request`：从内存读 MD 的请求（模式、列表、对话框），偏移从导出函数推导；先以只观察方式接到现有循环里，记录
   MD 请求与界面识别的对照。
2. 影子对局：重建后不在第一个决策点停下，按选择继续推进；暴露当前决策点；选项集对齐与 trace。
   已实现：`ygorl.selfplay.shadow`（`ShadowDuel`，自动回答记入 `log`，对手放弃了的应对记为 `could_respond`；对手回合开始即停）、
   `ygorl.selfplay.bridge`（`Request` / `Option` 数据模型、`align`），王牌融合一例在 `tests/test_selfplay.py` 离线复现。
3. 拆分 `mdplay`：`md.request`（读）、`bridge`（对齐）、`mdui`（点击，不做决策）、薄的循环；逐个删掉写死的规则，
   让影子对局 + 策略决策。
4. 对手回合的请求接策略（单步打分）；解码一回合一次与回合内效果，减少遮罩兜底。

**边角情况由 player 自己学会，不逐个写死。** 新卡、新效果总会带来没见过的对话框（效果选择、卡片选择、单选数量、
是 / 否……）。为每一种手写识别器与规则不可持续，拆成两层：

1. **选什么（决策）由影子对局 + 策略给出。** trace 显示 MD 的子选择大多在客户端对话框里完成，此时引擎输入状态是 0
   （不 accepting），所以只在 accepting 的请求上对齐的影子对局看不到它们，全落到了写死的规则（「是 / 否选否」「列表选第一张」
   「第一个可用效果」）。改为：自己动作之内，MD 每出一个自己的对话框（不论输入模式），读出对话框类型与选项
   （`md.request`：对话框选项的效果描述、列表候选的 password + 位置、单选的行数），与影子对局当前的决策点对齐
   （效果选择 ↔ `SelectOption`，列表 ↔ `SelectCard` / `SelectUnselectCard` / `SelectTribute`，是 / 否 ↔ `SelectEffectYn` /
   `SelectYesNo`，表示形式 ↔ `SelectPosition`，格子 ↔ `SelectPlace`，单选数量 ↔ `SelectOption` / 宣言数字）；
   策略在影子决策点上打分，选中的 ygopro 动作映射回 MD 的选项（卡按 password + 位置，效果按描述号，其余按值），
   再用同一个选择推进影子对局。对不上时这一步用规则兜底、丢弃影子对局并记一条不一致，到下一个命令点重建。
2. **怎么点（界面机制）由屏幕签名 + 探索 + 操作手册学会。**
   - **签名**：内存里的输入模式 / accepting / 对话框类型 / 列表类型 / 选项数，加画面上对话框面板的粗略指纹。
   - **可点元素**从截图里找，不按坐标写死：按钮（深色面板上的亮色文字块）、单选行（黄色圆圈）、列表卡（蓝色托盘）、
     标签页、高亮的卡（黄框）、命令图标（圆）。危险区一律不点：设置齿轮（投降入口）、Auto、聊天与系统按钮。
   - **探索**：没见过的签名、或手册里的做法失败时，按元素逐个试：先点「选项类」元素（第 1 层给出第几个），再点
     「确认类」按钮；每次点击后判断进展：内存（输入状态、对话框类型、局面键）变了，或签名变了。只改变了选中状态
     （签名不变、对话框局部变了）的继续点确认；没有进展的撤销（再点一次）后试下一个。探索有次数上限，用完交给自我恢复。
   - **操作手册**（`out/mdplay/playbook.json`，跨局累积）：成功的操作序列以相对元素描述记在签名下（如「第 k 个单选行 →
     确认按钮」），记成功 / 失败次数；同一签名再出现时直接用，失败降级并重新探索。现有写死的对话框脚本（是 / 否、列表、
     单选、效果标签页、表示形式）作为手册的种子条目。
   - 实现（`ygorl.md.explore`）补充的约定：第 1 层给的 `choice` 是同类选项类元素里的序号（单选从上到下，其余从左到右）；
     只有按钮的对话框里就是按钮序号（是 / 否：0 = 否，1 = 是）；「放弃 / 取消」是单独的意图（`decline`），手册里分开记。
     查手册的顺序：本签名学到的 → 同一画面指纹在其它内存状态下学到的 → 屏幕类别的种子 → 探索。得分 (成功 + 1) / (总次数 + 2)
     低于 0.5 的做法不再使用（降级）。探索时先「选项 + 确认」再单独的按钮（亮着的取消也算进展，不能先试）；只有看上去是
     是 / 否（没有其它选项、按钮全亮）时按钮优先。选项点击后对话框还在，即使内存变了也只算选中状态变化，继续点确认。
     进展默认由调用方用内存判断，`Explorer.screen_progress` 是只看签名的兜底。
   - 每次探索与手册命中都写进 trace，卡住记录照旧；目标是新对话框第一次出现时自己学会，第二次直接通过。

**手牌点击要核对，不靠排序假设。** 手牌在画面上的顺序是 MD 客户端自己的排序（不在 `duel.dll` 里），只能从观察归纳，
已经错过两次（通常怪兽排在效果怪兽前；一次把「沼泽王」的召唤点成了发动）。所以排序只用来猜第一下点哪张；点开后读左上角的
卡片信息面板（`ygorl.md.panel`）核对：卡名一行的图像与已学到的卡名比对，怪兽再读等级 / 攻击 / 守备数字与手牌里各卡的数值比对。
面板显示的不是目标卡就逐个点其它手牌位置找，找不到算卡住（交给自我恢复）。面板认不出来（还没学过）时沿用这一下点击，
等内存确认动作成功后，把当时的面板截图记成这张卡的卡名、并给数字打标签（`out/mdplay/panel_book.npz`，跨局累积）。
发动图标另按图标颜色识别（黄绿色），不按位置。根本解是读客户端（IL2CPP）里手牌视图的卡片列表，留作后续。

**自我恢复。** 单人模式自博弈不靠人在旁边盯着：卡住时 player 自己发现、记录、恢复，继续打。
- 发现：步骤里抛出的 `Stuck` 或任何异常、同一局面连续三步、长时间（240 秒）没有要它做的事、策略的意图没有在内存里兑现。
- 恢复按同一局面逐级升级：(1) 遮住刚才那个没兑现的动作，点一下棋盘空处关掉可能开着的卡，等画面静止后重新决策；
  (2)(3) 换一种回答当前对话框（列表里的下一张、是 / 否的另一个、提示取消、下一个高亮的卡），命令点则（失败的动作已遮住）重新决策；
  (4) 进入下一阶段。同一局面超过 4 次、一局超过 30 次才放弃。
- 每次恢复都写进 trace（原因、级别、卡住记录），所以「无干预地正确打完」可以量化：一局里没有放弃、恢复次数越少越好；
  每条卡住记录仍是补识别器、修 bug 的输入。
- 多局：`--games N` 在结果画面按「重试」开下一局，每局重新读对局状态的地址（新对局会重新分配）。

**当前实现（2026-10-22）**，`ygorl.selfplay.loop` / `trace` 与 `ygorl.md.layout` / `screen` / `input` / `ui`：

- **输入**：`XSendEvent` 直接发给游戏的 XWayland 窗口，用户自己的鼠标指针不动；每个事件前都重跑单人模式门禁。
- **坐标**：所有位置记在一个参考坐标系里（2054×1184 窗口、客户区 2048×1152 @ (3, 29)）。截图与点击只针对 Wine 的
  客户区子窗口，点击按实际客户区大小映射，截图重采样回参考坐标系。命令图标（召唤 / 盖放 / 发动 / 攻击 / 确认）在点击卡片
  前后各截一张图、找新出现的圆形图标；列表里的卡由下方蓝色托盘的宽度（每张 158 px）定位。
- **决策**：主要阶段 / 战斗阶段命令点由策略决定；自己动作之内的对话框（列表、场上目标与解放、效果选择、单选、是 / 否、
  表示形式、自己回合的连锁询问）先问影子对局（`ShadowObserver.choose`）：对上了就由策略在影子决策点上选，trace 记为
  `{"by": "shadow"}`；没有影子或对不上时退回写死的规则（`{"by": "rule"}`）并丢弃影子。对手回合里的询问仍是规则。
  界面种类靠截图识别。
- **点击与决策分开**：所有点击脚本在 `ygorl.md.ui`（上面的 mdui）：输入「做什么」（打开手牌、按第几个命令图标、
  选格子、选列表第几张、阶段菜单、攻击 / 确认目标、连锁询问发动或放弃），点击并看屏确认，返回看到的东西（图标、列表卡）；
  不含任何决策，鼠标与截图可注入，离线测试用假鼠标 + 合成截图。决策（策略与写死的规则）都留在 `loop.py`。
- **trace**：每次运行写一个 `out/mdplay/<run>.jsonl`（取代原来的 `log-*.json`），每个循环步一条：回合 / 阶段、MD 输入状态、
  识别出的对话框、内存摘要（双方 LP 与场上 (cid, 表侧, 横置)、自己的手牌；对手的手牌与里侧卡只记张数）、决策（策略动作与
  前几名概率，或所用规则）、点击、上一动作的检查结果、MD 拒绝、卡住原因；`--screen-every N` 每 N 步另存半分辨率截图
  （`.npz`）。`python -m ygorl.selfplay.trace SUMMARY <trace>` 汇总：决策种类计数、检查通过 / 失败、按原因的拒绝、卡住次数、
  每回合步数。
- **检查**：每个动作之后用内存核对策略的意图是否达成（召唤出表侧攻击表示、盖放出里侧……），不符或连续三步局面不变就停，
  写卡住记录（截图、内存状态、当前步与最近 30 条 trace 记录）到 `out/mdplay/stuck-*`。
- **对局结束**以 `DLL_DuelGetDuelFinish` 为准（混淆过的 LP 偶尔会在改写途中读成 0）；回合 / 阶段切换后等 2.5 秒动画。
- 手牌在画面上的顺序与内存不同：怪兽按等级，魔法先通常后速攻，再陷阱，组内按卡 id 升序。

## 架构

```
MD 进程 ──(只读内存 / 手写 JSON)──► BoardSnapshot ──► 重建 ×N 份样本 ──► 策略 ──► top-k 建议（终端）
                                   (公开信息 + 自己手牌)   (ygopro-core)      (load_actor)
```

- **`BoardSnapshot`**（`ygorl.advisor.snapshot`）：识别层与决策层之间唯一的接口。
  - 内容只有建议方能看到的东西：回合数、阶段、回合玩家、双方 LP、各区域的卡片及其表示形式、自己的手牌、对手手牌数、双方卡组剩余张数。
  - 卡片一律用 `password` 标识；对手的暗牌只记位置，不记卡名。
  - 可以写成 JSON，便于保存样本和回放测试。
  - 座位按建议方重排：建议方始终是 `0`，与游戏里的先后攻无关。
- **重建**（`ygorl.advisor.reconstruct`）：把快照放进 ygopro-core，让合法动作、`DecisionPoint` 和观测编码都能直接复用，不需要伪造核心的查询字节流。
  - 做法同 `engine/puzzle.py`：`OCG_DuelNewCard` 逐张放卡，起手张数和每回合抽卡都是 0。双方 LP 分别取快照值。
  - 核心开局总是先攻方第 1 回合的主要阶段 1。
    - 快照回合数 > 1 时加上 `DUEL_ATTACK_FIRST_TURN`，允许进入战斗阶段。
    - `DecisionPoint.turn` 改写成快照的回合数，观测里的回合特征由此保持正确。
  - 首版只支持**建议方自己回合的主要阶段 1**。主要阶段 2 近似处理：重建成主要阶段 1，再遮住「进入战斗阶段」。
  - 暗牌按样本填充，见下一条「采样」。
- **采样**：未知卡不能留空，否则引擎推出的合法动作就错了。每份样本单独补全以下三类：
  - **对手的暗牌**（手牌、盖放的卡、卡组）：按 HDT 过滤从环境 meta 卡组里抽取。
    - 先选出与对手已公开的卡相容的 meta 卡组，按占比加权选一套。
    - 再把这套卡组减去已公开的卡，从剩下的卡里抽。盖放的怪兽只从怪兽里抽，盖放的魔陷只从魔法、陷阱里抽。
    - 没有相容的卡组时，按占比从全部 meta 卡组里选。
  - **自己的卡组**：自己的完整卡组（`.ydk` 或 `ydke://`）减去已公开的卡，剩下的洗乱后作为卡组。
  - **自己的额外卡组**：额外卡组减去已在场上、墓地和除外区出现的额外卡组怪兽。

  各样本的动作分布按「动作种类 + 卡片 password + 效果描述」对齐后取平均。
- **决策**（`ygorl.advisor.advise`）：
  - 用 `train.checkpoint.load_actor` 读取策略，BC 与 PPO 检查点都能读。
  - 用 `env.observer.PointObserver` 编码观测。
  - 输出 top-k 动作、概率和各样本间的离散程度。
  - 只在重建出的第一个决策点给建议。选定一个动作后，局面变化要等下一张快照。
- **读取器**（`ygorl.md.memory`，T7.6）：在 Linux 上对 Proton 里的游戏进程做 `process_vm_readv`。
  - 读 MD 的原生规则引擎 `duel.dll`（不是 Unity 的 IL2CPP 层）：从 `/proc/<pid>/maps` 找到 `duel.dll` 的映射基址和磁盘路径，
    读它的全局对局状态指针，再按偏移读各字段。
  - **偏移不手写，从 `duel.dll` 自动推导**（`ygorl.md.offsets`）：解析 PE 导出表，用 GNU `objdump` 反汇编
    `DLL_DuelGetLP`、`DLL_DuelGetCardNum` 等查询函数，按指令模式取出位移。导出名在游戏更新后不变，地址和字段位置可以变，
    所以更新后读取器直接对新 DLL 重新推导，不需要人工 rebase；模式匹配不上时报 `OffsetError`，说明查询函数本身改了，要重新看反汇编。
  - 推导不出来的只有**标志位的含义**（正反面、守备表示、除外区里背面的位），它们要对着画面确定。按 DLL 的 sha256 记录在
    `src/ygorl/md/offsets_data/<sha256 前 16 位>.json`（`verified` + `semantics`）。没有记录或未核对的版本，
    `--attach --raw` 照常可用，生成快照会被拒绝。Steam `buildid` 只作显示。
  - MD 内部卡 id（`md_cid`）就是 Konami 卡片数据库 id（YgoMaster 的数据里 Blue-Eyes White Dragon 89631139 = 4007），
    YGOPRODECK 以 `misc_info.konami_id` 给出。映射表是环境产物 `artifacts/md_cid.json`，由 `tools/build_md_cid.py` 生成。
  - **只放建议方在画面上能看到的东西**：本地 `duel.dll` 可能存着对手的手牌、卡组和盖放卡，读取器一律不用。
    对手手牌和卡组只取张数，盖放 / 里侧的卡只取位置，背面除外的卡记为未知；`--raw` 的输出里对手场上的卡也一律隐藏。
  - 能读到的额外信息（一回合一次的已用标记、连锁、本回合事件）逐步补进快照，用来降低下述失真。

## 探路结论（T7.5 / T7.6，Steam buildid 23020425）

**可行，走 `duel.dll`。** `global-metadata.dat` 未加密（版本 31）；更直接的是规则引擎 `masterduel_Data/Plugins/x86_64/duel.dll`
（原生 PE，ImageBase `0x180000000`，203 个 `DLL_Duel*` 导出，YgoMaster 也调用同一组函数）。查询函数都很短，直接读一块全局状态。
下表是 `mdoffsets.derive` 在该版本上得到的结果（`S` = `[duel.dll + 0x11f9c50]`，`K` = `[duel.dll + 0x11f9c48]`，`p` 为 0/1）：

| 字段 | 位置 | 来源导出函数 |
|------|------|--------------|
| 回合玩家 / 回合数 / 阶段 | `S + 0x3c08` / `0x3c14` / `0x3c1c`（阶段 0 抽卡 … 2 主要 1、3 战斗、4 主要 2、5 结束） | `DLL_DuelWhichTurnNow` 等 |
| 本客户端的玩家号 | `K + 4` | `DLL_DuelGetMyPlayerNum` |
| LP | `S + p × 0xddc`，与 `K` 处的 16 位值异或 | `DLL_DuelGetLP` |
| 各区张数 | 玩家块 `+0x0c` 手牌、`+0x10` 卡组、`+0x14` 墓地、`+0x18` 额外、`+0x1c` 除外 | `DLL_DuelGetCardNum` |
| 场上格子 | 玩家块 `+0x5c + i × 0x1c`：`+0` 卡 id，`+2` uid 字，`+6` 横置（守备表示，`DLL_DuelGetCardTurn` 的 turn 是「转向」不是回合），`+7` 表侧，`+0xa` 效果链表头；i = 0–4 主要怪兽区、5–6 额外怪兽区、7–11 魔陷区、12 场地 | `DLL_DuelGetCardUniqueID` / `GetCardTurn` / `GetCardFace` |
| 手牌、卡组、额外、墓地、除外 | 玩家块 `+0x1e4`、`+0x3c4`、`+0x5a4`、`+0x7fc`、`+0xa54` 起，每张 4 字节：卡 id + uid 字 | `DLL_DuelGetCardUniqueID` |
| 除外的卡是否里侧 | 玩家块 `+0xcac + i × 2` 的字节，`0x80` 位为里侧 | `DLL_DuelGetCardFace`（locate 17） |
| uid → 卡 id | `S + 0x1bec + uid × 8`（uid < 512） | `DLL_DuelGetCardIDByUniqueID2` |
| 超量素材 | 效果链表节点 `S + 0x2bec + n × 16`：`+0` 代码，`+2` 种类，`+4` uid，`+0xc` 下一个；素材 = 代码 `0x3fb` 且种类低 4 位为 5 | `DLL_DuelGetThisCardOverlayNum` |

- uid 字的编码是 `uid = (w & 1) | (w >> 8) << 1`，低字节其余位是标志（墓地里 `0x40` 有特殊含义）。
- LP 的异或只是防篡改的混淆，读取时按函数里的做法还原即可。
- 2026-09-24 初稿把状态指针写成 `+0x11adc50`（差 `0x4c000`，把文件偏移当成了 RVA）；按初稿手写偏移的读取器会读到无关内存。
  改成自动推导后，这类抄写错误不会再出现。

**运行时核对（2026-10-21，单人模式，DLL sha256 `97bd4d13…`，Steam buildid 23020425 与 24462996 共用同一个 `duel.dll`）**：

- 表侧：表侧的场地魔法 `face = 0x01`，盖放的魔陷 `0x00`；盖放的怪兽 `face = 0x00`、横置 `0x01`，反转召唤后变成 `0x01` / `0x00`。
- 格子编号按控制者自己的视角（M1 = 自己最左边），画面上对手一侧左右镜像，与 ygopro-core 相同，不需要换算。
- 本地内存里确实有对手的手牌卡 id；快照与 `--raw` 都不输出它们。
- 结果记在 `src/ygorl/md/offsets_data/97bd4d136e39b087.json`（`verified: true`）。游戏更新时 sha256 不变就直接复用；
  变了就自动重新推导，标志位含义需要再按上面的步骤核对一次（盖放一只怪兽、反转召唤，看两个字节）。
- 还没在对局中见过：额外怪兽区左右与格子 5 / 6 的对应。里侧除外的位由反汇编得到。

剩下的失真（本回合已召唤 / 已改变表示形式、一回合一次）见下一节；状态字（格子 `+0x10`）在反转召唤后变化，可能包含这些标志，待解读。
读取器始终只读。

## 重建的已知失真

| 丢失的信息 | 影响 | 处理 |
|------------|------|------|
| 事件历史（`events` 窗口为空） | 信念相关特征、「不响应」证据全部缺失 | 在建议中注明；B4 读到本回合事件后转成 `M.Message` 补上 |
| 一回合一次的已用标记、通常召唤已用 | 可能建议已经用过的效果或召唤 | 首版注明；B4 读到后在建议里剔除对应动作 |
| 持续效果的附带状态（装备对象、指示物、效果赋予的状态） | 部分卡的效果和数值不对 | 首版注明 |
| 连锁进行中、对方回合、战斗步骤中 | 不支持 | 首版只在自己回合的空闲点给建议 |
| 核心里的回合数是 1 | 依赖回合数的脚本（极少）可能不同 | 观测层改写 `turn`；脚本层差异注明 |

## MD 与 ygopro-core 的规则差异

| 差异 | 影响 | 处理 |
|------|------|------|
| 规则判定按 OCG（英文客户端显示 TCG 文本） | Project Ignis 脚本以 TCG/OCG 通用判定为主，个别卡与 MD 结算不同 | 文档化；发现具体卡再记入本表 |
| 会赢下对局的循环最多执行 10 次 | 核心没有循环上限，理论上能无限循环 | 忽略：自博弈已有 `max_decisions` 上限 |
| 墓地里选取对象的顺序可能与实体卡不同 | 只影响显示和选择顺序，不影响合法性 | 忽略 |
| 排位赛是 Bo1、没有副卡组 | 环境的 `deck.side_max` 应为 0 | 从下一个环境版本起由 `ygorl env build` 写入 `side_max: 0` |
| 计时：开局 300 秒 + 每回合 90 秒 | 策略与搜索的时间预算 | 环境清单新增可选 `match` 段记录；只作元数据 |
| 没有 Speed / Rush 模式 | 无 | 无 |

`md-2026-09` 不改：环境指纹会哈希 `environment.json`，改动会让已训练产物的环境戳全部失效。新规则从下一个版本（如 `md-2026-10`）起生效。

## 评估

1. **重建保真**：在自博弈中随机取建议方自己回合主要阶段 1 的决策点，从真实状态导出 `BoardSnapshot` 后重建，再比较两边的合法动作集合和观测。
   - 每张卡的「已用标记」不一致可以接受。
   - 报告动作集合的重合率。
   - 只采对手暗牌与真实情况完全一致的样本，单独度量重建本身的误差。
2. **信息损失的代价**：同一批决策点上，比较「重建后的策略 top-1」和「原局面里的策略 top-1」的一致率。
3. **读取器**：在单人模式对局里用 `--attach` 导出快照，与画面人工核对 LP、阶段和各区域卡片。

实测（`md-2026-09`，327 个决策点）：合法动作 Jaccard 0.91，策略 top-1 与真实局面一致 78%，对手先验用真实卡组与用 meta 卡组几乎相同；
差异几乎全是本回合已用的效果与召唤。数字与方法见 [benchmarks.md](../benchmarks.md)「MD 建议器：重建保真」。

## 卡组互通

- 支持社区常用的 `ydke://` 链接：`ydke://` 后接 `main!extra!side` 三段 base64，每段是按小端 u32 排列的 `password`。

# Master Duel 集成：数据对齐与只读建议器

> 属于 [ygorl 设计文档](README.md)。状态：草案（2026-09-24；2026-10-21 增加「单人模式自动对局」），属于首期之后的扩展（见 [06-architecture.md](06-architecture.md) §5.2「对局接口」）。

## 定位与边界

目标：让训练好的策略在 Master Duel（MD）的真实对局里使用，形态是**只读建议器**（advisor）。它读取局面，在终端给出候选动作及其概率，由人自己决定是否照做。这是研究原型，用来衡量策略在真实对局分布上的表现，**不是 bot**：

- 不向游戏发送任何输入：不模拟点击，不注入按键，不调用游戏函数。唯一的例外是下文「单人模式自动对局」，
  它是单独的、需要显式开启的工具，只在对手是电脑时动作。
- 不往游戏进程写内存，不注入 DLL，不 hook。
- 不抓包，不改网络协议。
- 状态来源只有两种：手写或保存下来的盘面快照，以及从游戏进程外部**只读**读取内存（与 Untapped.gg Companion 同类）。

Konami《使用条款》第 3 节禁止自动化软件、bot、未授权第三方软件和逆向工程，所以读取器即便只读也有账号风险，见 [08-risks.md](08-risks.md)。开发与验证优先在单人模式（Solo）里进行。

## 单人模式自动对局（Solo 自博弈，草案）

用户 2026-10-21 决定：在单人模式里让策略自己打 MD，用来在真实 MD 规则与真实电脑对手上评估策略、积累对局数据。
用户知情并接受账号风险（Konami《使用条款》第 3 节明确禁止自动化软件和 bot，这一项比只读读取器风险更高）。边界：

- **只在对手是电脑时动作，失败即停（fail-closed）。** 每个决策前读 `duel.dll` 的玩家类型（`DLL_DuelIsHuman` 读的
  `K + 8 + p × 4`：0 = 人，单人模式里电脑为 1）：对手类型不是已核对过的电脑值、读不到、或 `duel.dll` 的偏移未核对，
  就不发送任何输入并退出。PvP（排位、活动、好友对战）永远不会动作。
- **输入只走操作系统层的模拟输入**，作用在游戏窗口上，与人用鼠标点击等价；仍然不写游戏内存、不注入 DLL、不 hook、不碰网络。
- **状态来源与建议器相同**：只读读取 → `BoardSnapshot` → 重建 → 策略。动作只从建议方可见的信息里选，与人打时一样。
- **动作 → 点击**：把重建里的 `Action` 映射成画面上的点击序列（选卡 → 选命令 → 选目标 / 区域 / 确认）。
  每次点击后重新读内存，确认局面按预期变化，不符就停，不盲点。
- 需要显式开启（单独运行 `python -m ygorl.selfplay.loop`），默认关闭；建议器 `ygorl advise` 本身仍然只读。
- 记录每局：快照序列、所选动作、结果，作为「真实 MD 规则下的评估」数据，绑定环境版本。

### 自博弈的架构：MD 管状态，ygopro 管规则与决策

**目标。** 规则基本一致，所以同一局面下 MD 给出的选项应当与 ygopro 的动作列表相同；UI 与结算动画不同只是「怎么点」的问题。
自博弈因此不为每种界面写决策规则，而是：**从 MD 读出状态与它正在问的问题，映射到 ygopro 的决策点，由策略在 ygopro 的选项里选，
再把选中的选项点出来。** 两边的选项集对不上的地方，就是重建的失真或真正的规则差异，记录下来，而不是猜。

**可行性检验（2026-10-21，单人模式，阿尔卡纳骑士小丑卡组）。** 在 MD 发动「王牌融合」之前的局面重建进 ygopro，走同一条线，
逐个决策点对照：

| 步骤 | ygopro | MD |
|------|--------|----|
| 发动「王牌融合」 | `SelectPlace`（5 个魔陷格子） | 选格子 ✓ |
| 对手的连锁窗口 | `SelectChain`：「堕天使与圣天使」或放弃 | 无。这张卡是给对手暗牌采样出来的，并不存在 ✗ |
| 自己的连锁窗口 | `SelectChain`：只有放弃 | 无（只有一个选项时 MD 不问） |
| 融合怪兽 | `SelectCard` 3 张「阿尔卡纳骑士小丑」选 1 | 列表 ✓ |
| 融合素材 | `SelectUnselectCard` {卡组「王后骑士」×3、手牌「卫兵骑士」、场上「国王骑士」} 选 3 | 逐张问：卫兵骑士、国王骑士；卡组的王后骑士自动补上 ✓（同一集合，问法不同） |

结论：**自己一方的动作，两边问的问题与候选一致**；差异有规律：(1) MD 跳过只有一个选项的决策，多选进行到一半时剩下的选项全等（同名同位置）也自动补齐；新的决策即使选项全等也照问（3 张同名融合怪兽）；
(2) 多选在 MD 里逐张问；(3) ygopro 会让**对手**用采样出来的暗牌做出 MD 里不存在的应对。同一局里还出现了第二类差异：
ygopro 让「小丑骑士」攻击，MD 不给攻击命令（多半是「王牌融合」发动后本回合只有融合怪兽能攻击，这类持续到回合结束的效果
不在快照里）。

**MD 的「问题」可以从内存读出来，不必看图猜。** 引擎的输入状态（`S + 0x3cd0` 模式、`+0x3cdc` 是否在等、`+0x3d00` 等谁）
说明在等哪一类输入；选卡列表在 `[duel.dll + 0x11f9c30]`（`DLL_DuelList*` 读的结构：头部 `+0x1` 最多选几张、`+0x2` 列表种类、
`+0xa` 张数，`+0x1a` 起每项 4 字节的 uid 字，`+0x4c8` 起每项来源位置），已在王牌融合的素材列表上核对；对话框（是 / 否、
表示形式掩码 `S + 0x3cb8` 等）由 `DLL_DuelDlg*` 读。偏移同其它字段一样从导出函数推导。列表里只有给建议方选的卡，
本来就在画面上，不涉及暗牌。

**请求的读取：没有列表的选卡（2026-10-23 审计，build 23020425）。** 有些选卡（输入模式 8）根本不用选卡列表：
`DLL_DuelComGetCommandMask` 对每个（玩家、位置、序号）调用 `S + 0x3d18` 处的**检查函数**，返回 `0x1000` 的卡就是候选，
列表里留着的是上一次选择的内容（张数 0，或别处的卡）。卡片的程序在 `.rdata` 的 32 字节表项里登记自己的检查函数
（u16 卡片 id、u16、u32，再是条件 / 检查 / 处理三个指针）。`S + 0x3cf0` 是发问的卡（卡片 id），`S + 0x3d08` / `+0x3d0c`
是它的位置（0–12 场上格子，13 手牌）/ 序号。已建模的检查只有一个：`duel.dll` RVA `0x5fca40`「发问玩家手牌中除发问卡以外的
任意 1 张」（见习魔术师、捣蛋鬼、梦魇见习魔术师、魔术师的见习黑魔术少女、古斯塔夫火箭：丢 1 张手牌特殊召唤），
候选 = 手牌去掉 `(0x3d08, 0x3d0c)` 那张；录制里 19 次见习魔术师的丢弃全部吻合（画面张数 = 手牌 − 1，丢掉的牌在候选里），
以前读出的是空列表或过期列表，策略只能按规则点第一张。RVA `0x2ad0c0`「通过发问卡自身过滤条件的手牌」（348 处引用，
例：千年启示）无法离线求值，读成「没有候选」（7 次录制里列表都是空的或上一次检索留下的卡组 / 墓地卡）；其它检查（如
上级召唤的祭品 `0x5a5140`）照旧读列表。这些 RVA 与 `S` 偏移不从导出函数推导，按 build 记在偏移文件的 `semantics`
（`REQUEST_SEMANTICS`）里，缺了就按旧办法读。

同一审计的另两处：「愚蠢的埋葬」的卡组列表读得没错（候选恰是卡组里全部怪兽），错在对齐：影子对局把剩下的卡组 / 额外卡组
洗过，MD 的牌堆序号对不上影子里的卡，14 个候选只配上 0 或 1 个；卡组、额外卡组的候选现在按卡（任一张同名卡）配对。
「太阳神之翼神龙」通常召唤后「支付基本分到剩 100」的诱发在 MD 里是一张只含神龙本身的列表，读出的候选正确；
规则代点是因为影子对局在上级召唤的祭品选择时已经失步（祭品由规则点，影子没有跟上），不是读请求的问题。

**客户端的命令掩码（2026-10-23 逆向，build 23020425，`ygorl.md.client`）。** 原则：能从内存读的都从内存读，画面只给点击位置。
以前「MD 允不允许召唤 / 盖放 / 发动 / 攻击 / 改变表示形式」靠找命令图标，误拒过合法动作、点过熔岩的黄光；连锁询问里的
多张卡逐个位置盲勾。逆向结论：

- `duel.dll` **不存**命令掩码。`DLL_DuelComGetCommandMask`（`0x1805a5970`，按 `S + 0x3cd0` 模式减 1 查 RVA `0x5a6048` 的跳转表）
  每次现算：空闲 / 战斗模式下手牌走 `0x1805a3d00`、怪兽区 `0x1805a4240`、魔陷区 `0x1805a45e0`、牌堆 `0x1805a4930 | 0x1805a4a30`；
  开放时点 / 连锁（模式 4 / 5）走 `0x1805a4bb0`，取连锁顶（`*(dll + 0x11f9c58) + 0x700 + (n − 1) * 0x38`，n 在 `+0xa84`）
  再调「能否发动」（场上 `0x180219830`、手牌 `0x180219fa0`），后者组出临时的发动上下文、执行卡片自己的条件代码。
  唯一的副作用是把理由码写进 `S + 0x3d14`。重新实现等于重写全部卡片程序，不可行。
- 结果在 **C# 客户端（IL2CPP 堆）** 里，三处可读：
  1. **打开的卡**：`YgomGame.Duel.CommandOperation`（`RunEffectWorker.<commandOperation>` 持有的唯一实例）：玩家 / 位置 / 序号、
     卡 id、精确的 `commandMask` 与按图标顺序排列的 `commandList`（命令编号）。卡关上后玩家为 −1。实测：手牌怪兽 `0x50`
     [4, 6]（召唤、盖放怪兽）、魔法 `0x88` [3, 7]（发动、盖放）、只能盖放的魔陷 `0x80` [7]、攻击中的怪兽 `0x1` [0]。
  2. **全场高亮**（点之前就有）：每张卡的视图 `CardRoot`（team / position / index / cardId / uniqueId）→ `CardPlane`：
     `highlightEff` 非空即 MD 正在高亮它，此时 `auraEffType` 才有意义（不亮时保留旧值）。`CardPlace.GetActivateAura` 用
     `ComGetCommandMask & 0x7fd`（`EffectTaskWaitInput.cmdBitHighlight`，除「查看」与投降以上的所有命令）决定亮不亮，
     光效编号说明掩码里有哪一组命令（见下表）。开放时点 / 连锁询问里只有可发动的卡亮。高亮在模式变化后 0.2–2 s
     （客户端的 WaitInput 任务开始时）才设好。
  3. **连锁 / 开放时点的卡片列表**：`CardSelectionList`（`CreateActivableList` 对手牌、场上、墓地、卡组逐张调
     `ComGetCommandMask`，有发动位的生成一个 `ListCardData`）：`m_ListType` 6 = 连锁（模式 5）、7 = 时点（模式 4），
     `m_GroupedDataList` 按列表顺序（可能分组嵌套）存 `ListCardData`：`cardid` 与 `cardstatus`。`cardstatus` 是
     BitVector32 的五个区段描述（i16 掩码、i16 位移：玩家、位置、序号、表示、回合）加数据 `bitVec`，按描述解码即得
     （玩家, 位置, 序号），再用局面读出 uid。实测两次单张询问都是魔陷区 7 的那张，而同一时刻 `duel.dll` 的请求没有候选。
     列表在询问结束后保留旧内容，只在请求种类是 open / chain 时有效。

玩家怎么用（`ygorl.selfplay.loop`）：主要 / 战斗阶段决策前读高亮，手牌 / 场上的卡不亮就遮住它的全部动作，亮的只留它光效组
里的命令（`Player.md_offers`，遮住的记在 trace 的 `md_masked`）；点开手牌后读 `CommandOperation`，掩码里没有要的命令就
直接判为 MD 不允许，有就按命令列表的序号点图标（不再按图标颜色猜）；连锁 / 开放询问按客户端列表的张数与顺序找策略要的卡，
勾选后仍读内存确认。读不到客户端时一律退回原来的画面判断。

命令位（客户端枚举 `CommandBit`，第 n 位 = 命令编号 n）与光效组（`CardPlace.commandPowerList`，实测各格相同）：

| 位 | 命令 | 种类 | 组 |
|----|------|------|----|
| `0x1` | Attack | attack | 2 |
| `0x2` | Look（查看） | — | 不亮 |
| `0x4` | SummonSp（卡片自身程序的特殊召唤） | spsummon | 3 |
| `0x8` | Action（发动） | activate | 3 |
| `0x10` | Summon（通常 / 上级召唤） | summon | 2 |
| `0x20` | Reverse（反转召唤） | flip | 2 |
| `0x40` | SetMonst（盖放怪兽） | mset | 2 |
| `0x80` | Set（盖放魔陷） | sset | 1 |
| `0x100` | Pendulum（作为灵摆刻度发动） | activate | 3 |
| `0x200` / `0x400` | TurnAtk / TurnDef（改变表示形式） | reposition | 1 |
| `0x800` / `0x1000` / `0x2000` | Surrender / Decide（模式 8 的选卡） / Draw | — | 不亮 |

光效编号（`CardPlane.ReqHighlight` 的映射，`+1` 表示这张卡正打开着）：`0x7c` / `0x7d` 只有组 1；`0x18` / `0x19` 有组 2
（可能带组 1）；`0x7e` / `0x7f` / `0x88` / `0x89` 有组 3（可能带组 1，也可能带组 2：run s30 里 `0x7e` 的卡掩码是 `0x54`，所以这几个值不排除任何命令）；`0xed` / `0xee` 组 2 与组 3 都有。所以高亮只给
「可能的种类」的上界，精确的掩码要打开那张卡读 `CommandOperation`。实测空闲时只能改变表示形式的怪兽是 `0x7c`，
没有任何命令的手牌不亮，每张亮着的卡打开后的掩码都落在它的组里。

**偏移在运行时推导。** 托管字段的偏移不写死：类名在映射进进程的 `global-metadata.dat`（版本 31）的字符串表里，扫可写内存
找 `+0x10` 指向类名、`+0x18` 指向命名空间的 `Il2CppClass`，从它 `+0x80` 的 `FieldInfo` 数组（每项 0x20：名字、类型、所属类、
偏移）按名字取字段偏移；实例按类指针扫描，再用引用的对象核对（`CommandOperation.worker` 是 `RunEffectWorker`、
`CardSelectionList.m_DuelClient` 是 `DuelClient`、`CardRoot` 的 `cardPlane` 是 `CardPlane`），核对失败（新对局、对象释放）就重扫。
写死的只有 IL2CPP 运行时结构本身（对象头 0x10、`List<T>` 的 `_items` / `_size`、数组数据 `+0x20`）。找类约 2 s，之后每次读几微秒。
卡的视图有对象池（位置 18 = 未用），新卡上场可能新建视图：自己的手牌 / 场上有卡没找到视图时重扫（至多每 5 s 一次）。
对手的卡一律不返回（打开的是对手的卡时不给卡 id）。

**待核对。** 多张卡的询问里列表顺序是否就是画面上的顺序（只见过单张）；墓地 / 除外的卡出现在询问列表与 `CommandOperation`
里的样子（墓地查看器打开的卡是否同样写入 `CommandOperation`）；`m_ListType` 之外是否需要再用打开标志判断列表正在显示。
接入（取代 `ygorl.md.ui` 的图标判断与 `ygorl.md.request` 的盲勾）另行进行。

**组件。**

```
MD 进程 ─► md.memory  局面（BoardSnapshot）
        └► md.request MD 在问什么：种类、候选（uid → password + 位置）、选几张          ─┐
                                                                                        ├─► bridge：MD 请求 ↔ ygopro 决策点
ygopro 影子对局 ◄── 在命令点从快照重建；在自己的一个动作之内与 MD 同步前进            ─┘     对齐选项集、记录不一致
策略 ◄── ygopro 的观测与动作列表（遮住 MD 不允许的）                                         │
mdui  ◄── 「选第 k 个选项」→ 点击（布局、图标检测；不做任何决策）                        ◄───┘
trace ◄── 每一步：MD 请求、ygopro 选项、选择、点击、之后的局面
```

- **命令点**（自己回合的主要阶段 / 战斗阶段命令）：从快照重建影子对局（同现在的建议器）。
- **自己动作之内**：影子对局与 MD 同步：用同一个选择推进影子对局，到下一个决策点时与 MD 读出的请求对齐。
  - 影子对局里只有一个可选项（取消、取消选择不算）、或多选进行中剩下的选项全等的决策，自动回答（MD 不问）；命令点总是问。
  - 影子对局里**对手**的决策一律放弃 / 不应对；对手真的应对了，MD 的局面会与影子对局不同（下一条）。
  - 多选：MD 逐张问，桥逐张把影子对局的选择喂进去。
- **重新同步**：MD 是状态的权威，ygopro 是合法性与决策的权威。影子对局与 MD 读出的局面不一致（对手应对、抽到的卡、
  检索到的卡、掷硬币）时，在下一个命令点从 MD 重建；动作之内对不上时，当前这一步改用 MD 自己的选项集（列表候选与
  ygopro 动作按 password + 位置对应；对不上的选项不选），这一步记为不一致。
- **对手回合里问到自己**（连锁、发动时点）：无法在连锁中途重建，影子对局不参与；从当前局面重建到同一回合、同一阶段的
  发动时点，由策略打分「发动 / 放弃」（见下文「动作之内的决策从当前局面重建」，近似写明）。
- **选项集不一致是数据，不是故障**：每一条记录 MD 请求、ygopro 决策、差集，按原因归类（采样的暗牌、本回合效果、
  一回合一次、MD 合并 / 跳过、规则差异）。已确定的原因进遮罩（如「本回合盖放的陷阱不能发动」「已攻击过」），
  其余的进「重建的已知失真」一节。

**重建能还原什么、不能还原什么。** 能：场上 / 手牌 / 墓地 / 除外 / 卡组构成、LP、表示形式、超量素材、阶段，以及本回合的
状态（2026-10-22 起，见下文「本回合状态的解码」）：每只怪兽本回合怎么上场的（通常 / 特殊 / 反转召唤、盖放）、是否已攻击、
是否改变过表示形式，每张场上的卡本回合是否发动过效果、魔陷本回合是否发动，通常召唤次数（原来把特殊召唤也算成了通常召唤），
以及读到的玩家效果链表（本回合追加的上级召唤等，读取器实时可读，录制里没有）。这些在重建开局后、主要阶段 1 开始时写进核心：
卡片状态（`STATUS_SUMMON_TURN` 等，因此改变表示形式、盖放回合的陷阱由核心自己禁止）、已攻击的怪兽不能再攻击、
`Duel.IncreaseSummonedCount`、追加上级召唤效果，以及用掉一回合一次（`Effect.UseCountLimit`）：场上的卡「本回合发动过效果」
且它在当前位置只有一个次数限制（或几个限制共用一个计数代码）时用掉它，本回合发动过的表侧魔陷用掉其发动的次数，
本回合发动后已离场的卡（由自博弈循环记下的发动历史，`BoardSnapshot.activated`）用掉其发动的次数。

不能（目前）：一张卡有几个各自一回合一次的效果时用的是哪一个（MD 的标志只按卡记，如「千年的启示」），离场的卡在读取器单独
附着时的发动记录（需要循环的历史），玩家效果链表之外的持续效果（上面的攻击限制）、装备 / 指示物以外的效果附带状态、
连锁中途的局面、对手的暗牌（采样，因此对手的决策不可信）。这些仍由「MD 不给这个命令」
的信号兜底：MD 的命令图标就是它对这张卡的命令掩码，没有对应图标的动作视为被 MD 禁止，遮住后重新决策；同一战斗阶段有两只怪兽的攻击被拒绝时，视为全阶段的攻击限制
（如「暗之门」按本阶段已经攻击过的次数判断，重建里没有这个计数），本阶段不再攻击。

**指标**（每局的 trace 汇总）：选项集一致率（按决策种类）、策略意图达成率（动作后的局面检查）、卡住次数与原因、
需要回退到规则的步数。目标是只靠脚本跑完整局：卡住为 0，回退步数逐局下降。

**迁移步骤**（每步单独可用）：
1. `md.request`：从内存读 MD 的请求（模式、列表、对话框），偏移从导出函数推导；先以只观察方式接到现有循环里，记录
   MD 请求与界面识别的对照。
2. 影子对局：重建后不在第一个决策点停下，按选择继续推进；暴露当前决策点；选项集对齐与 trace。
   已实现：`ygorl.selfplay.shadow`（`ShadowDuel`，自动回答记入 `log`，对手放弃了的应对记为 `could_respond`；对手回合开始即停）、
   `ygorl.selfplay.bridge`（`Request` / `Option` 数据模型、`align`），王牌融合一例在 `tests/test_selfplay.py` 离线复现。
3. 拆分 `mdplay`：`md.request`（读）、`bridge`（对齐）、`mdui`（点击，不做决策）、薄的循环；逐个删掉写死的规则，
   让影子对局 + 策略决策。
4. 对手回合的请求接策略（单步打分）；解码一回合一次与回合内效果，减少遮罩兜底。
   已实现前半：`ygorl.selfplay.decide`（攻击对象、表示形式、发动询问从当前局面重建），`ygorl.selfplay.audit` 离线度量。

**边角情况由 player 自己学会，不逐个写死。** 新卡、新效果总会带来没见过的对话框（效果选择、卡片选择、单选数量、
是 / 否……）。为每一种手写识别器与规则不可持续，拆成两层：

1. **选什么（决策）由影子对局 + 策略给出。** trace 显示 MD 的子选择大多在客户端对话框里完成，此时引擎输入状态是 0
   （不 accepting），所以只在 accepting 的请求上对齐的影子对局看不到它们，全落到了写死的规则（「是 / 否选否」「列表选第一张」
   「第一个可用效果」）。改为：自己动作之内，MD 每出一个自己的对话框（不论输入模式），读出对话框类型与选项
   （`md.request`：对话框选项的效果描述、列表候选的 password + 位置、单选的行数），与影子对局当前的决策点对齐
   （效果选择 ↔ `SelectOption`，列表 ↔ `SelectCard` / `SelectUnselectCard` / `SelectTribute`，是 / 否 ↔ `SelectEffectYn` /
   `SelectYesNo`，表示形式 ↔ `SelectPosition`，格子 ↔ `SelectPlace`，单选数量 ↔ `SelectOption` / 宣言数字）；
   策略在影子决策点上打分，选中的 ygopro 动作映射回 MD 的选项（卡按 password + 位置，效果按描述号，其余按值），
   再用同一个选择推进影子对局。对不上时这一步用规则兜底、丢弃影子对局并记一条不一致，到下一个命令点重建。
2. **怎么点（界面机制）由屏幕签名 + 探索 + 操作手册学会。**
   - **签名**：内存里的输入模式 / accepting / 对话框类型 / 列表类型 / 选项数，加画面上对话框面板的粗略指纹。
   - **可点元素**从截图里找，不按坐标写死：按钮（深色面板上的亮色文字块）、单选行（黄色圆圈）、列表卡（蓝色托盘）、
     标签页、高亮的卡（黄框）、命令图标（圆）。危险区一律不点：设置齿轮（投降入口）、Auto、聊天与系统按钮。
   - **探索**：没见过的签名、或手册里的做法失败时，按元素逐个试：先点「选项类」元素（第 1 层给出第几个），再点
     「确认类」按钮；每次点击后判断进展：内存（输入状态、对话框类型、局面键）变了，或签名变了。只改变了选中状态
     （签名不变、对话框局部变了）的继续点确认；没有进展的撤销（再点一次）后试下一个。探索有次数上限，用完交给自我恢复。
   - **操作手册**（`out/mdplay/playbook.json`，跨局累积）：成功的操作序列以相对元素描述记在签名下（如「第 k 个单选行 →
     确认按钮」），记成功 / 失败次数；同一签名再出现时直接用，失败降级并重新探索。现有写死的对话框脚本（是 / 否、列表、
     单选、效果标签页、表示形式）作为手册的种子条目。
   - 实现（`ygorl.md.explore`）补充的约定：第 1 层给的 `choice` 是同类选项类元素里的序号（单选从上到下，其余从左到右）；
     只有按钮的对话框里就是按钮序号（是 / 否：0 = 否，1 = 是）；「放弃 / 取消」是单独的意图（`decline`），手册里分开记。
     查手册的顺序：本签名学到的 → 同一画面指纹在其它内存状态下学到的 → 屏幕类别的种子 → 探索。得分 (成功 + 1) / (总次数 + 2)
     低于 0.5 的做法不再使用（降级）。探索时先「选项 + 确认」再单独的按钮（亮着的取消也算进展，不能先试）；只有看上去是
     是 / 否（没有其它选项、按钮全亮）时按钮优先。选项点击后对话框还在，即使内存变了也只算选中状态变化，继续点确认。
     进展默认由调用方用内存判断，`Explorer.screen_progress` 是只看签名的兜底。
   - 每次探索与手册命中都写进 trace，卡住记录照旧；目标是新对话框第一次出现时自己学会，第二次直接通过。

**识别与执行的系统化（2026-10-22 重构）。** 一天的实战把 bug 归成三类，逐个打补丁止不住，按类修：

1. **「在问什么」由内存决定，画面只负责「点哪里」。** 之前每个对话框识别器都按第一个关卡测的颜色和位置写死，换了熔岩场地
   （暗色背景）后横幅、是 / 否、表示形式、图标、高亮依次误判。改为：
   - **判定**：谁持有输入（`player` / `accepting`）+ MD 的请求（输入模式、对话框类型 `dialog_type`、列表类型与张数、
     对话框参数）决定是哪一类问题；画面识别只在内存说不清时（同一对话框类型的不同画面）作补充，并且只认「有按钮 /
     有可点元素」的正面证据，不再用「某块区域偏暗」这类背景相关的判据。已观察到的对话框类型：6 效果选择、10 表示形式、
     13 单选、26 / 59 卡片列表（59 为多选）、0 无对话框。
   - **不是自己的输入一律等待**：对手持有输入时不点任何东西（除了不属于任何一方的提示与被最小化的面板）。
   - **回归语料**：每条卡住记录（截图 + 内存状态）都标注真值（画面类别、可点元素位置），成为测试用例；识别器的任何改动都要
     在整个语料上不退化。卡住记录同时写下完整的请求（含 `dialog_type`），语料随实战自动增长。
2. **「点到的是不是那张卡」先核对再提交。** 手牌顺序、列表顺序、图标种类都曾靠猜，造成了把错的卡盖放、送墓、复活、
   当成对象（审计发现列表多选 4 次全错，一次「发动」点成了改变表示形式）。统一成一个原语：点开 → 核对身份（信息面板的卡名 /
   数值、图标的字形）→ 确认无误才提交；核对不出来就**放弃这个动作**（遮住，让策略换一个），而不是猜。
3. **动作之后按预期的具体变化核对。** 「棋盘有变化」太宽松（改变表示形式被当成发动成功）。按动作种类核对具体变化：
   哪张卡离开了哪里、到了哪里、表示形式是否该变；有影子对局时用它推进后的局面作为预期。

**动作之内的决策从当前局面重建（2026-10-22）。** 审计实战 trace 发现，动作之内的子选择几乎都落到了规则：攻击对象从不问影子
对局；表示形式对话框在影子对不上时一律表侧攻击（3 只「拉的使徒」攻击表示，多掉 5500 LP）；效果选择退回「第一个可用效果」；
对手回合的询问只在对手战斗阶段发动（放过了一次「灵魂交错」）；动作之后 MD 问的第一个问题约 40% 与影子对局对不上。两类修法：

1. **影子对局容忍 MD 已知的问法差异**（`ShadowObserver.choose`），不再一对不上就丢弃：
   - MD 先问表示形式、后问格子（ygopro 相反）；魔法的代价 / 对象也在格子之前问。影子停在自己的 `SelectPlace` 时，先用玩家
     稍后要点的格子（没有就第一个空格）推进，再对齐 MD 的问题。
   - 效果选择：ygopro 每个效果是一个单独的发动动作，MD 点卡后才用标签页问。策略选的发动动作的描述号就是标签页：
     MD 的卡片字符串 `cid | (10 + n) << 16` 对应 `aux.Stringid(password, n)` = `password << 20 | n`（Project Ignis 的
     `utility.lua`；原先按 `password × 16 + n` 换算，一次都没对上）。
   - MD 问了影子自动回答过的问题（只有一张候选、同名的卡）：用影子当时的回答（`ShadowObserver.pending`），只有一种卡时
     记为 `forced`，影子保留。
   - 诱发效果的「是否发动」（`SelectEffectYn`）就是 MD 的发动询问；MD 也会把它并进候选卡列表（「拉的使徒」的列表，取消 = 否）：
     列表即「是」，策略的倾向记在 `policy_yes`。
2. **答得出来的问题从当前局面重建再问策略**（`ygorl.selfplay.decide`，`Decider`）：影子不在或对不上时，从 MD 此刻的
   局面（`situation`：任何回合、任何阶段读成建议器能重建的快照）重建，把核心带到问同一个问题的决策点，按暗牌样本平均策略的
   概率（同 `advise`），trace 记为 `{"by": "rebuild", "question": ..., "probs": ...}`；都不行才用规则。
   - **攻击对象**：重建战斗阶段，执行策略选的攻击，核心随后的 `SelectCard`（对方的怪兽）就是这个问题，打分取最大。精确到暗牌。
     第一个样本的影子推进过对象后接回 `ShadowObserver`（`adopt`），伤害步骤里的询问继续同步。攻击决策的 trace 带
     `"target": {"by": "rebuild" | "rule", ...}`。
   - **表示形式**：板面脚本给被召唤的怪兽登记一个一次性的永续效果，在主要阶段 1 开始时把它表侧特殊召唤，核心自己问
     `SelectPosition`。效果挂在这只怪兽自己身上：「拉的使徒」只放行使徒自己效果的特殊召唤。哪只怪兽：MD 对话框参数里的卡
     （mix 种类 5）→ 影子的 `SelectPosition` → 策略的特殊召唤动作 → 自从策略的动作以来离开了牌堆（手牌、卡组、额外、墓地、
     除外）却还不在场上的那只（`in_limbo`）→ 这个动作里 MD 列出的候选只有一种怪兽（使徒的列表）。**近似**：局面是召唤前的，
     召唤它的那个效果（代价、结算的其余部分）不在重建里。
   - **发动询问**（对手回合与自己的结束阶段 / 战斗阶段）：核心不能从连锁中途开始，重建也只从自己的主要阶段 1 开始，
     所以由主机把核心带到同一回合玩家、同一阶段：对手回合时先结束自己的回合（对手的手牌先少一张、卡组多一张，重建里的抽卡
     补回来），对手的回合由固定脚本走（进战斗阶段、用第一只能攻击的怪兽攻击一次、主要阶段 2、结束阶段），核心沿途给建议方的
     开放时点（`SelectChain` / `SelectEffectYn`）。取 MD 所在阶段里给出建议方发动最多的那个时点（内存列出了 MD 提供的卡时
     只算这些卡），策略的「发动」概率之和与「放弃」比较。**近似**：引出 MD 这次询问的事件（对手的发动、召唤、此前的连锁）
     不在重建里，时点是同一阶段的开放时点；依赖事件历史的诱发（「这张卡送去墓地的回合」）在重建里不会出现，这时退回规则。
     自己回合主要阶段里的询问（自己动作之内的连锁）只由影子对局回答。
   - 离线度量：`python -m ygorl.selfplay.audit [--policy CKPT] out/mdplay/2026102*.jsonl` 在 trace 记下的局面上重放这些
     决策（卡组按 trace 里见过的自己的卡近似），统计当时与现在各由谁决定。

主循环相应地从一长串 if / elif 改成**分派表**：键是（谁持有输入, 内存里的请求种类, 画面类别），值是处理函数；
「不是自己的」「画面还没稳定」「内存与画面不一致」各有一处统一处理，新问题加一行表项与一个处理函数，不再改动其它分支。

**手牌点击要核对，不靠排序假设。** 手牌在画面上的顺序是 MD 客户端自己的排序（不在 `duel.dll` 里），只能从观察归纳，
已经错过两次（通常怪兽排在效果怪兽前；一次把「沼泽王」的召唤点成了发动）。所以排序只用来猜第一下点哪张；点开后读左上角的
卡片信息面板（`ygorl.md.panel`）核对：卡名一行的图像与已学到的卡名比对，怪兽再读等级 / 攻击 / 守备数字与手牌里各卡的数值比对。
面板显示的不是目标卡就逐个点其它手牌位置找，找不到算卡住（交给自我恢复）。面板认不出来（还没学过）时沿用这一下点击，
等内存确认动作成功后，把当时的面板截图记成这张卡的卡名、并给数字打标签（`out/mdplay/panel_book.npz`，跨局累积）。
发动图标另按图标颜色识别（黄绿色），不按位置。根本解是读客户端（IL2CPP）里手牌视图的卡片列表，留作后续。

**自我恢复。** 单人模式自博弈不靠人在旁边盯着：卡住时 player 自己发现、记录、恢复，继续打。
- 发现：步骤里抛出的 `Stuck` 或任何异常、同一局面连续三步、长时间（240 秒）没有要它做的事、策略的意图没有在内存里兑现。
- 恢复按同一局面逐级升级：(1) 遮住刚才那个没兑现的动作，点一下棋盘空处关掉可能开着的卡，等画面静止后重新决策；
  (2)(3) 换一种回答当前对话框（列表里的下一张、是 / 否的另一个、提示取消、下一个高亮的卡），命令点则（失败的动作已遮住）重新决策；
  (4) 进入下一阶段。同一局面超过 4 次、一局超过 30 次才放弃。
- 每次恢复都写进 trace（原因、级别、卡住记录），所以「无干预地正确打完」可以量化：一局里没有放弃、恢复次数越少越好；
  每条卡住记录仍是补识别器、修 bug 的输入。
- 多局：`--games N` 在结果画面按「重试」开下一局，每局重新读对局状态的地址（新对局会重新分配）。
  赢了的单人决斗没有「重试」，只有「确认」，之后回到关卡菜单。用户允许 player 点这段菜单（2026-10-22）：
  `ygorl.md.menu.MenuWalker` 只认得 VICTORY、LEVEL & EXP 的返回、通关奖励弹窗的确认、关卡列表（先点新解锁的白框关卡，
  否则当前关卡）和关卡页的「玩」，只点这些固定目标，直到新对局开始。菜单里对局状态已被 MD 释放，单人模式门禁无法运行，
  所以菜单点击走 `MenuMouse`：对局进行中一律拒绝，其余的防护就是「只点认得的画面上的固定目标」。

**当前实现（2026-10-22）**，`ygorl.selfplay.loop` / `trace` 与 `ygorl.md.layout` / `screen` / `input` / `ui`：

- **输入**：`XSendEvent` 直接发给游戏的 XWayland 窗口，用户自己的鼠标指针不动；每个事件前都重跑单人模式门禁。
  但 Wine 把窗口内的按下当作用户点击，会激活窗口、抢走用户的焦点；所以长时间自博弈应让游戏跑在单独的、不可见的
  X 显示器上，截图与输入按 `YGORL_MD_DISPLAY` 指向它（缺省 `:0`）。做法见 `tools/md_display.sh`：sway 跑在
  wlroots 的 headless 后端上，只有一个 2048×1152 输出，Xwayland 在 `:2`（Steam 启动项 `DISPLAY=:2 %command%`），
  游戏按窗口类名全屏、无边框；wayvnc 推送这个输出供人观看（`vncviewer localhost:5900`，只绑定 127.0.0.1）。
  截图走合成器（`grim`，wlroots screencopy），不用 `xwd`：全屏的游戏窗口由 Xwayland 直接把缓冲区翻给合成器，X 窗口自己的
  像素不再更新，`xwd` 截到的画面落后一秒以上，玩家会点在已经消失的界面上。游戏窗口还必须拿着 sway 座位的焦点，否则
  Wine 丢掉合成的点击。
  试过而不可用的：Xvfb 没有 DRI3，DXVK 只能退到 wined3d CPU 渲染；weston 只开 vnc 后端时也没有 DRI3，开
  headless + vnc 两个输出时游戏落在 headless 那个上（kiosk 的 app-ids 对 Xwayland 窗口无效），VNC 看到全黑；
  x11vnc 在 Xwayland 上只能整窗轮询，很卡。游戏内分辨率要设为 2048×1152：窗口被裁掉一部分时 `xwd` 只截到可见
  部分，缩小重采样后面板与图标模板也都不成立，它们只在原生 2048×1152 下测量过。
- **坐标**：所有位置记在一个参考坐标系里（2054×1184 窗口、客户区 2048×1152 @ (3, 29)）。截图与点击只针对 Wine 的
  客户区子窗口，点击按实际客户区大小映射，截图重采样回参考坐标系。命令图标（召唤 / 盖放 / 发动 / 攻击 / 确认）在点击卡片
  前后各截一张图、找新出现的圆形图标；列表里的卡由下方蓝色托盘的宽度（每张 158 px）定位。
- **决策**：主要阶段 / 战斗阶段命令点由策略决定；自己动作之内的对话框（列表、场上目标与解放、效果选择、单选、是 / 否、
  表示形式、自己回合的连锁询问）先问影子对局（`ShadowObserver.choose`）：对上了就由策略在影子决策点上选，trace 记为
  `{"by": "shadow"}`；没有影子或对不上时，攻击对象、表示形式与发动询问（含对手回合）从当前局面重建后由策略决定
  （`{"by": "rebuild"}`，`ygorl.selfplay.decide`），仍不行才退回写死的规则（`{"by": "rule"}`）。
  界面种类靠截图识别；没有脚本的界面、未知的输入模式与自我恢复的第 3 级交给 `ygorl.md.explore`（探索 + 操作手册
  `out/mdplay/playbook.json`），以内存（输入状态、对话框、列表张数、局面键）变化为进展。
- **点击与决策分开**：所有点击脚本在 `ygorl.md.ui`（上面的 mdui）：输入「做什么」（打开手牌、按第几个命令图标、
  选格子、选列表第几张、阶段菜单、攻击 / 确认目标、连锁询问发动或放弃），点击并看屏确认，返回看到的东西（图标、列表卡）；
  不含任何决策，鼠标与截图可注入，离线测试用假鼠标 + 合成截图。决策（策略与写死的规则）都留在 `loop.py`。
- **trace**：每次运行写一个 `out/mdplay/<run>.jsonl`（取代原来的 `log-*.json`），每个循环步一条：回合 / 阶段、MD 输入状态、
  识别出的对话框、内存摘要（双方 LP 与场上 (cid, 表侧, 横置)、自己的手牌；对手的手牌与里侧卡只记张数）、决策（策略动作与
  前几名概率，或所用规则）、点击、上一动作的检查结果、MD 拒绝、卡住原因；每步另存对局状态块的原始内存（`<run>-memory/`，对手的玩家块、
  唯一 id 表与效果链表清零，保证对手的暗牌不离开内存），供离线解码一回合一次与回合内效果；`--screen-every N` 每 N 步另存半分辨率截图
  （`.npz`）。`python -m ygorl.selfplay.trace SUMMARY <trace>` 汇总：决策种类计数、检查通过 / 失败、按原因的拒绝、卡住次数、
  每回合步数。
- **检查**：每个动作之后用内存核对策略的意图是否达成（召唤出表侧攻击表示、盖放出里侧……），不符或连续三步局面不变就停，
  写卡住记录（截图、内存状态、当前步与最近 30 条 trace 记录）到 `out/mdplay/stuck-*`。
- **对局结束**以 `DLL_DuelGetDuelFinish` 为准（混淆过的 LP 偶尔会在改写途中读成 0）；回合 / 阶段切换后等 2.5 秒动画。
- 手牌在画面上的顺序与内存不同：怪兽按等级，魔法先通常后速攻，再陷阱，组内按卡 id 升序。这只是猜测，打开的是哪张卡
  一律读内存确认（`ygorl.md.selection`）：打开一张卡时，游戏在 IL2CPP 堆上的一个界面对象里写入相邻的两个 u32
  （卡 id, 对局 uid），同一对象 0x78 之后还存着上一张。对象地址每次运行才知道：扫描可写内存中自己手牌的 (卡 id, uid)
  相邻对（约 10 处、1.6 秒），打开另一张卡后再扫一次，值变成另一张手牌的那一处就是它（「上一张」那一处的新值等于它的
  旧值，排除）；之后每次打开读一次即知是哪一张实例。读出的不是自己的卡就作废、重新校准。信息面板的图像识别
  （`ygorl.md.panel`）只在校准之前兜底。
- **宣言卡名**：搜索框要点两下才真正拿到键盘焦点（第一下只把框描亮，此时打的字不进框），用退格清空（不用框右的 X），
  打字后按回车执行搜索（放大镜与点别处都不执行）；结果放在灰色托盘上，点第一张再按 Select。先宣言只含字母、数字与
  空格的名字、怪兽优先；MD 答「No applicable cards found」就换下一个名字。
- **墓地发动**：点自己的墓地堆（右侧牌组上方，(1600, 812)）打开查看器：右缘一列竖排（x 1946，从 y 280 起每张 150），
  最上面是墓地最上一张，即内存里墓地顺序的反序。按内存顺序算出该卡的位置并点开，打开的是哪张卡读内存确认
  （`ygorl.md.selection`，墓地卡同样写入那个界面对象），不是就试下一个位置；确认之后才点它新出现的发动图标（位置未测，
  只在墓地堆上方 (1624, 690) ±80 的框里找字形为发动的图标：更大的框把熔岩的黄光当成过图标，点了三次都没反应）。
  内存确认是那张卡而 MD 不给发动（灰的或根本没有图标）时，本回合内都遮住这个动作（只遮本阶段时策略又选了七次）。
  除外的卡的发动仍未支持。
- **连锁询问里的多张卡**：MD 可以把几张可发动的卡并排放进同一个询问（中心 (1026, 934)，间距 166 px）；内存里的
  请求此时没有候选，所以逐个位置勾选、读内存，直到勾到策略要的那张。
- **MD 不显示的列表候选**：内存的选卡列表里有、MD 的画面列表里却始终没有的卡（「愚蠢的埋葬」的卡组列表里的
  「太阳神之翼神龙-不死鸟」，四次都翻完整个列表、逐张由内存认出也没有它）：翻完仍没见到就记下（password, 位置）并存到
  `out/mdplay/md_hidden_in_lists.json`，之后同样的列表把它排除在影子对局的选项之外，让策略在 MD 显示的卡里选。
- **硬币**（「时间魔术师」）：MD 自己的「Coin Toss Selection」对话框，引擎此时不接受输入（模式 0），只能看画面
  （两枚硬币上方的绿色圆圈）；两面概率相同，按规则选左边再按 OK（曾经干等 10 分钟，这一局被放弃）。
- **太阳神之翼神龙支付基本分**：特殊召唤后的可选诱发是一张只含神龙的列表（左边取消）。策略管不到它，规则：只在
  神龙本回合能攻击时（自己的主要阶段 1，且不是对局第一回合）支付，否则取消（第一回合付到 100、下回合即输）。
- **场上卡的两个图标**（发动与改变表示形式）各在卡左右约 86 px，在卡的 x ±230 内找；改变表示形式取不是发动的那个。
- **列表的卡从客户端的列表读**：客户端的 `CardSelectionList` 也装着每个选卡列表（种类 8 / 10 等），顺序与画面一致
  （run s33 的列表逐张核对过）；对手的卡只记位置不读卡号。要选的卡直接按它在列表里的序号点（超出画面的先按箭头翻到
  最右），点后读打开的卡确认；读不到或对不上再逐张勾选。内存的请求列表过期时（千年启示的代价），候选也改取客户端的列表。
- **列表里的同名卡**：同名卡在不同位置（手牌的与卡组的「黑魔术师」）只能靠内存读出的 uid 区分；规则选卡时取卡组的那张。
  第一次打开手牌之前就出现的列表（第一回合「愚蠢的埋葬」）在列表自身的勾选上校准内存地址。
- **放弃的对局**：同一局面恢复 4 次仍不行就放弃这一局；系列赛不就此结束，而是从对局内设置（左上齿轮 → Retry → Yes）
  重开这一局，接着打。

## 架构

```
MD 进程 ──(只读内存 / 手写 JSON)──► BoardSnapshot ──► 重建 ×N 份样本 ──► 策略 ──► top-k 建议（终端）
                                   (公开信息 + 自己手牌)   (ygopro-core)      (load_actor)
```

- **`BoardSnapshot`**（`ygorl.advisor.snapshot`）：识别层与决策层之间唯一的接口。
  - 内容只有建议方能看到的东西：回合数、阶段、回合玩家、双方 LP、各区域的卡片及其表示形式、自己的手牌、对手手牌数、双方卡组剩余张数。
  - 卡片一律用 `password` 标识；对手的暗牌只记位置，不记卡名。
  - 可以写成 JSON，便于保存样本和回放测试。
  - 座位按建议方重排：建议方始终是 `0`，与游戏里的先后攻无关。
- **重建**（`ygorl.advisor.reconstruct`）：把快照放进 ygopro-core，让合法动作、`DecisionPoint` 和观测编码都能直接复用，不需要伪造核心的查询字节流。
  - 做法同 `engine/puzzle.py`：`OCG_DuelNewCard` 逐张放卡，起手张数和每回合抽卡都是 0。双方 LP 分别取快照值。
  - 核心开局总是先攻方第 1 回合的主要阶段 1。
    - 快照回合数 > 1 时加上 `DUEL_ATTACK_FIRST_TURN`，允许进入战斗阶段。
    - `DecisionPoint.turn` 改写成快照的回合数，观测里的回合特征由此保持正确。
  - 首版只支持**建议方自己回合的主要阶段 1**。主要阶段 2 近似处理：重建成主要阶段 1，再遮住「进入战斗阶段」。
  - 暗牌按样本填充，见下一条「采样」。
- **采样**：未知卡不能留空，否则引擎推出的合法动作就错了。每份样本单独补全以下三类：
  - **对手的暗牌**（手牌、盖放的卡、卡组）：按 HDT 过滤从环境 meta 卡组里抽取。
    - 先选出与对手已公开的卡相容的 meta 卡组，按占比加权选一套。
    - 再把这套卡组减去已公开的卡，从剩下的卡里抽。盖放的怪兽只从怪兽里抽，盖放的魔陷只从魔法、陷阱里抽。
    - 没有相容的卡组时，按占比从全部 meta 卡组里选。
  - **自己的卡组**：自己的完整卡组（`.ydk` 或 `ydke://`）减去已公开的卡，剩下的洗乱后作为卡组。
  - **自己的额外卡组**：额外卡组减去已在场上、墓地和除外区出现的额外卡组怪兽。

  各样本的动作分布按「动作种类 + 卡片 password + 效果描述」对齐后取平均。
- **决策**（`ygorl.advisor.advise`）：
  - 用 `train.checkpoint.load_actor` 读取策略，BC 与 PPO 检查点都能读。
  - 用 `env.observer.PointObserver` 编码观测。
  - 输出 top-k 动作、概率和各样本间的离散程度。
  - 只在重建出的第一个决策点给建议。选定一个动作后，局面变化要等下一张快照。
- **读取器**（`ygorl.md.memory`，T7.6）：在 Linux 上对 Proton 里的游戏进程做 `process_vm_readv`。
  - 读 MD 的原生规则引擎 `duel.dll`（不是 Unity 的 IL2CPP 层）：从 `/proc/<pid>/maps` 找到 `duel.dll` 的映射基址和磁盘路径，
    读它的全局对局状态指针，再按偏移读各字段。
  - **偏移不手写，从 `duel.dll` 自动推导**（`ygorl.md.offsets`）：解析 PE 导出表，用 GNU `objdump` 反汇编
    `DLL_DuelGetLP`、`DLL_DuelGetCardNum` 等查询函数，按指令模式取出位移。导出名在游戏更新后不变，地址和字段位置可以变，
    所以更新后读取器直接对新 DLL 重新推导，不需要人工 rebase；模式匹配不上时报 `OffsetError`，说明查询函数本身改了，要重新看反汇编。
  - 推导不出来的只有**标志位的含义**（正反面、守备表示、除外区里背面的位），它们要对着画面确定。按 DLL 的 sha256 记录在
    `src/ygorl/md/offsets_data/<sha256 前 16 位>.json`（`verified` + `semantics`）。没有记录或未核对的版本，
    `--attach --raw` 照常可用，生成快照会被拒绝。Steam `buildid` 只作显示。
  - MD 内部卡 id（`md_cid`）就是 Konami 卡片数据库 id（YgoMaster 的数据里 Blue-Eyes White Dragon 89631139 = 4007），
    YGOPRODECK 以 `misc_info.konami_id` 给出。映射表是环境产物 `artifacts/md_cid.json`，由 `tools/build_md_cid.py` 生成。
  - **只放建议方在画面上能看到的东西**：本地 `duel.dll` 可能存着对手的手牌、卡组和盖放卡，读取器一律不用。
    对手手牌和卡组只取张数，盖放 / 里侧的卡只取位置，背面除外的卡记为未知；`--raw` 的输出里对手场上的卡也一律隐藏。
  - 能读到的额外信息（一回合一次的已用标记、连锁、本回合事件）逐步补进快照，用来降低下述失真。

## 探路结论（T7.5 / T7.6，Steam buildid 23020425）

**可行，走 `duel.dll`。** `global-metadata.dat` 未加密（版本 31）；更直接的是规则引擎 `masterduel_Data/Plugins/x86_64/duel.dll`
（原生 PE，ImageBase `0x180000000`，203 个 `DLL_Duel*` 导出，YgoMaster 也调用同一组函数）。查询函数都很短，直接读一块全局状态。
下表是 `mdoffsets.derive` 在该版本上得到的结果（`S` = `[duel.dll + 0x11f9c50]`，`K` = `[duel.dll + 0x11f9c48]`，`p` 为 0/1）：

| 字段 | 位置 | 来源导出函数 |
|------|------|--------------|
| 回合玩家 / 回合数 / 阶段 | `S + 0x3c08` / `0x3c14` / `0x3c1c`（阶段 0 抽卡 … 2 主要 1、3 战斗、4 主要 2、5 结束） | `DLL_DuelWhichTurnNow` 等 |
| 本客户端的玩家号 | `K + 4` | `DLL_DuelGetMyPlayerNum` |
| LP | `S + p × 0xddc`，与 `K` 处的 16 位值异或 | `DLL_DuelGetLP` |
| 各区张数 | 玩家块 `+0x0c` 手牌、`+0x10` 卡组、`+0x14` 墓地、`+0x18` 额外、`+0x1c` 除外 | `DLL_DuelGetCardNum` |
| 场上格子 | 玩家块 `+0x5c + i × 0x1c`：`+0` 卡 id，`+2` uid 字，`+6` 横置（守备表示，`DLL_DuelGetCardTurn` 的 turn 是「转向」不是回合），`+7` 表侧，`+0xa` 效果链表头；i = 0–4 主要怪兽区、5–6 额外怪兽区、7–11 魔陷区、12 场地 | `DLL_DuelGetCardUniqueID` / `GetCardTurn` / `GetCardFace` |
| 手牌、卡组、额外、墓地、除外 | 玩家块 `+0x1e4`、`+0x3c4`、`+0x5a4`、`+0x7fc`、`+0xa54` 起，每张 4 字节：卡 id + uid 字 | `DLL_DuelGetCardUniqueID` |
| 除外的卡是否里侧 | 玩家块 `+0xcac + i × 2` 的字节，`0x80` 位为里侧 | `DLL_DuelGetCardFace`（locate 17） |
| uid → 卡 id | `S + 0x1bec + uid × 8`（uid < 512） | `DLL_DuelGetCardIDByUniqueID2` |
| 超量素材 | 效果链表节点 `S + 0x2bec + n × 16`：`+0` 代码，`+2` 种类，`+4` uid，`+0xc` 下一个；素材 = 代码 `0x3fb` 且种类低 4 位为 5 | `DLL_DuelGetThisCardOverlayNum` |

- uid 字的编码是 `uid = (w & 1) | (w >> 8) << 1`，低字节其余位是标志（墓地里 `0x40` 有特殊含义）。
- LP 的异或只是防篡改的混淆，读取时按函数里的做法还原即可。
- 2026-09-24 初稿把状态指针写成 `+0x11adc50`（差 `0x4c000`，把文件偏移当成了 RVA）；按初稿手写偏移的读取器会读到无关内存。
  改成自动推导后，这类抄写错误不会再出现。

**运行时核对（2026-10-21，单人模式，DLL sha256 `97bd4d13…`，Steam buildid 23020425 与 24462996 共用同一个 `duel.dll`）**：

- 表侧：表侧的场地魔法 `face = 0x01`，盖放的魔陷 `0x00`；盖放的怪兽 `face = 0x00`、横置 `0x01`，反转召唤后变成 `0x01` / `0x00`。
- 格子编号按控制者自己的视角（M1 = 自己最左边），画面上对手一侧左右镜像，与 ygopro-core 相同，不需要换算。
- 本地内存里确实有对手的手牌卡 id；快照与 `--raw` 都不输出它们。

## 重建的已知失真

| 丢失的信息 | 影响 | 处理 |
|------------|------|------|
| 事件历史（`events` 窗口为空） | 信念相关特征、「不响应」证据全部缺失 | 在建议中注明；B4 读到本回合事件后转成 `M.Message` 补上 |
| 一回合一次的已用标记、通常召唤已用 | 可能建议已经用过的效果或召唤 | 已解码（格子 `+0x14`、玩家块 `+0x30` / `+0x34`、玩家效果链表、发动历史）并写进核心；一张卡几个效果各自一回合一次时不知道用了哪个，仍靠 MD 拒绝兜底 |
| 持续效果的附带状态（装备对象、指示物、效果赋予的状态） | 部分卡的效果和数值不对 | 首版注明 |
| 连锁进行中、对方回合、战斗步骤中 | 不支持 | 首版只在自己回合的空闲点给建议；Solo 自博弈的发动询问用同阶段的开放时点近似（「动作之内的决策从当前局面重建」） |
| 正在进行的召唤（表示形式对话框） | 召唤它的效果不在重建里 | 用一次性效果在主要阶段 1 开始时特殊召唤同一只怪兽，问核心自己的 `SelectPosition` |
| 核心里的回合数是 1 | 依赖回合数的脚本（极少）可能不同 | 观测层改写 `turn`；脚本层差异注明 |

## MD 与 ygopro-core 的规则差异

| 差异 | 影响 | 处理 |
|------|------|------|
| 规则判定按 OCG（英文客户端显示 TCG 文本） | Project Ignis 脚本以 TCG/OCG 通用判定为主，个别卡与 MD 结算不同 | 文档化；发现具体卡再记入本表 |
| 会赢下对局的循环最多执行 10 次 | 核心没有循环上限，理论上能无限循环 | 忽略：自博弈已有 `max_decisions` 上限 |
| 墓地里选取对象的顺序可能与实体卡不同 | 只影响显示和选择顺序，不影响合法性 | 忽略 |
| 排位赛是 Bo1、没有副卡组 | 环境的 `deck.side_max` 应为 0 | 从下一个环境版本起由 `ygorl env build` 写入 `side_max: 0` |
| 计时：开局 300 秒 + 每回合 90 秒 | 策略与搜索的时间预算 | 环境清单新增可选 `match` 段记录；只作元数据 |
| 没有 Speed / Rush 模式 | 无 | 无 |

`md-2026-09` 不改：环境指纹会哈希 `environment.json`，改动会让已训练产物的环境戳全部失效。新规则从下一个版本（如 `md-2026-10`）起生效。

## 评估

1. **重建保真**：在自博弈中随机取建议方自己回合主要阶段 1 的决策点，从真实状态导出 `BoardSnapshot` 后重建，再比较两边的合法动作集合和观测。
   - 每张卡的「已用标记」不一致可以接受。
   - 报告动作集合的重合率。
   - 只采对手暗牌与真实情况完全一致的样本，单独度量重建本身的误差。
2. **信息损失的代价**：同一批决策点上，比较「重建后的策略 top-1」和「原局面里的策略 top-1」的一致率。
3. **读取器**：在单人模式对局里用 `--attach` 导出快照，与画面人工核对 LP、阶段和各区域卡片。

实测（`md-2026-09`，327 个决策点）：合法动作 Jaccard 0.91，策略 top-1 与真实局面一致 78%，对手先验用真实卡组与用 meta 卡组几乎相同；
差异几乎全是本回合已用的效果与召唤。数字与方法见 [benchmarks.md](../benchmarks.md)「MD 建议器：重建保真」。

## 卡组互通

- 支持社区常用的 `ydke://` 链接：`ydke://` 后接 `main!extra!side` 三段 base64，每段是按小端 u32 排列的 `password`。
- `ydke://` 链接和 `.ydk` 文件在所有接受卡组的命令行参数里通用。
- MD 客户端自身导出卡组要经 Konami 卡片数据库中转，转成 `.ydk` 用外部工具 DawnbrandBots/deck-transfer-for-master-duel（[07-building-blocks.md](07-building-blocks.md)）。
